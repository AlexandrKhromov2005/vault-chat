# Vault Chat

Корпоративный командный мессенджер на Go с отдельными сервисами Auth, Chat,
Media и API Gateway. Проект находится в разработке: авторизация доступна через
REST; комнаты, отправка сообщений и история доступны через авторизованный Chat API,
события в реальном времени — через WebSocket.

Статус ниже отражает реализацию на 17 октября 2026 года.
Первый релиз backend MVP — `v0.1.0`. [История изменений](CHANGELOG.md)
и [правила версионирования](VERSIONING.md) описывают состав и порядок выпуска.
[Архитектура](ARCHITECTURE.md) описывает целевую систему; не все её компоненты
уже реализованы.
[Требования и план подготовки к защите](docs/requirements.md) содержат статусы
обязательных компонентов, задачи до коллоквиума и экзамена и критерии готовности.

## Что уже есть

| Компонент | Реализовано | Доступность |
|---|---|---|
| Auth | Регистрация, вход, Argon2id, JWT RS256 и проверка access token | Запускаемый gRPC-сервис; публичный профиль по ID и поиск по началу имени через Gateway |
| Сессии | Хранение в PostgreSQL, refresh rotation, обнаружение повторного использования refresh token, logout и выход со всех устройств | gRPC и REST через Gateway |
| Gateway | REST для Auth, комнат и сообщений Chat, WebSocket для событий, профили пользователей по ID и поиск по имени, проверка токена через Auth, rate limiting по IP и пользователю через Redis, CORS, ограничения тела и времени запроса, recovery, опциональный TLS 1.3 | Запускаемый HTTP-сервис |
| Комнаты Chat | Уникальный личный диалог на пару пользователей с указанием обоих участников, каналы с владельцем, добавление и удаление участников владельцем, выход из канала, состав комнаты и чтение только для участников, список комнат пользователя по последней активности с курсором | Go-сервис, отдельная PostgreSQL-БД, авторизованный gRPC и REST через Gateway |
| Сообщения Chat | Неизменяемый текст до 4096 символов, проверка членства, повторная отправка по UUID без дубликатов, история с курсором, номер сообщения в комнате и догрузка пропущенных сообщений после известной позиции, публикация событий о сообщениях и составе комнат в Redis Pub/Sub после фиксации | PostgreSQL, gRPC и REST через Gateway |
| Реальное время | Chat публикует события о сообщениях и составе комнат в Redis Pub/Sub после фиксации только участникам комнаты; Gateway доставляет их по WebSocket с авторизацией первым сообщением, продлением токена без переподключения, пингами, лимитами и закрытием медленных клиентов; пропущенное догружается по `after` | WebSocket через Gateway, несколько экземпляров Gateway через общий Redis |
| Контракт Chat | Protobuf-контракт операций с комнатами и событий, сгенерированный gRPC-код | Реализованы все десять RPC; актор проверяется через Auth |
| Данные | Миграции пользователей и сессий Auth, отдельные миграции комнат, участников и сообщений Chat | Auth и Chat применяют миграции своих отдельных БД при запуске |
| Наблюдаемость | JSON-логи через `slog`, request ID через HTTP → gRPC, `/health` и `/ready` у Gateway | Реализовано для Auth/Chat/Gateway |
| Проверки | Unit-, PostgreSQL integration- и race-тесты, 33 цели фаззинга, проверка `govulncheck`, конфигурации golangci-lint, buf и mockery | Локальные проверки |
| Media | Загрузка и скачивание закрытых файлов, метаданные в отдельной БД, текущие права участника комнаты, вложения в сообщениях, истории и WebSocket; лимит 10 МиБ и проверка содержимого | gRPC и REST; [правила и ограничения](docs/media/files.md) |
| Инфраструктура | Docker Compose с отдельными PostgreSQL для Auth, Chat и Media, Redis, NATS и MinIO; общий `Dockerfile` для Go-сервисов (distroless, non-root), healthchecks и порядок старта | Auth, Chat, Media и Gateway с тремя PostgreSQL, Redis и S3 запускаются одной командой; NATS остаётся опциональным |

Правила и ограничения комнат описаны в [документации Chat](docs/chat/rooms.md).
Chat хранит свои данные отдельно и не обращается к таблицам Auth.

## Чего не хватает до MVP

Цель MVP из архитектуры: **Auth, личные сообщения, каналы, загрузка файлов и
запуск четырёх сервисов через Docker Compose**.

- [x] Авторизация и управление сессиями.
- [x] REST Gateway для Auth.
- [x] Внутреннее ядро комнат и проверки членства/прав владельца.
- [x] Получение профиля по ID в Auth и проверка существования получателя в Chat.
- [x] Поиск пользователей по имени для удобного выбора собеседника.
- [x] Запускаемый Chat-сервис: конфигурация, отдельная БД, применение миграций,
  gRPC-обработчики с проверкой токена и доступом через Gateway.
- [x] Список комнат и необходимые операции управления участниками.
- [x] Отправка и хранение сообщений, история с курсорной пагинацией,
  ограничения размера и защита от дубликатов при повторной отправке.
- [x] WebSocket: авторизованные подписки, доставка событий и восстановление
  пропущенных сообщений после переподключения.
- [x] Media-сервис: загрузка в MinIO, метаданные, скачивание и проверка доступа
  к вложениям, ограничения размера и типа файлов.
- [x] Обновление Go и зависимостей с проверкой `govulncheck`.
- [x] Контейнеризация Auth, Gateway, Chat и Media; запуск всего MVP одной командой.
- [x] Сквозной тест: два пользователя входят, создают диалог, обмениваются
  сообщениями и вложением; третий не получает доступ к чужому диалогу.

Для ручного показа есть [минимальный веб-клиент](#веб-клиент): вход, поиск,
комнаты, переписка, участники, вложения и события в реальном времени, а также
[сценарий демонстрации](docs/demo.md).

### Ближайший порядок разработки

1. Закрыть требования к кэшу и брокеру: согласовать трактовку с преподавателем,
   подготовить сценарий кэширования данных и сохраняемый поток событий при необходимости.
2. Добавить C1/C2, зоны доверия, модель угроз и ADR.
3. К экзамену реализовать и проверить транспортную защиту, балансировку,
   наблюдаемость, нагрузку, отказы и восстановление данных по
   [плану подготовки](docs/requirements.md).
4. Media и вложения реализованы в текущем блоке MVP; обязательность для курса
   по-прежнему уточняется отдельно.

### Остальные запланированные возможности

Пока отсутствуют организации и команды, полноценный RBAC, TOTP/2FA,
поиск по сообщениям, треды, реакции, редактирование/удаление сообщений,
presence и уведомления. Также не реализованы mTLS между сервисами, E2EE,
аудит административных действий, Prometheus/Grafana, OpenTelemetry и Kubernetes.
Приоритет этих функций после MVP нужно определять отдельно.

## Текущие ограничения

- Logout и отзыв сессий блокируют дальнейшее обновление токенов. Уже выданный
  access token действует до истечения срока, по умолчанию 15 минут.
- Gateway → Auth/Chat и Chat → Auth используют gRPC без TLS. Публичный TLS Gateway включается
  отдельно через сертификат и ключ в конфигурации.
- При недоступности Redis rate limiter пропускает запросы; IP определяется
  по адресу соединения, без поддержки доверенных reverse proxy.
- Chat проверяет токен и существование получателя через Auth. Профиль по ID
  и результаты поиска содержат только ID и имя пользователя. Любой авторизованный
  пользователь может перебрать каталог по префиксам имён; это сдерживают только
  лимит запросов на пользователя и страница не более 50 записей.
- Публичные и приватные каналы пока используют приглашения. Поиск публичных
  каналов и самостоятельное вступление не реализованы.
- Chat ставит события в ограниченную очередь в памяти процесса
  (`CHAT_EVENT_QUEUE_SIZE`) и публикует их одним фоновым обработчиком. При
  переполнении новые события отбрасываются с предупреждением в логе, при
  остановке очередь дописывается не дольше `CHAT_EVENT_DRAIN_TIMEOUT`.
- События реального времени доставляются без гарантии: при сбое Redis или
  разрыве соединения клиент догружает пропущенное по номерам сообщений.
  Открытое WebSocket-соединение живёт до истечения access token, даже если
  сессии отозваны. Лимиты WebSocket-соединений на пользователя, общий
  (`GATEWAY_WS_MAX_CONNECTIONS`) и для ещё не авторизованных
  (`GATEWAY_WS_MAX_UNAUTHENTICATED_CONNECTIONS`) действуют в пределах одного
  экземпляра Gateway; лимита на весь кластер и на IP-адрес нет, поэтому при
  недоступном Redis клиенты без токена могут занять все слоты для
  неавторизованных соединений и задержать подключение остальных. При остановке
  Gateway закрывает все соединения кодом 1001 и ждёт завершения закрытия не
  дольше 15 секунд.
- Передачи владения каналом нет, поэтому владелец не может покинуть канал или
  быть удалён из него.

`govulncheck` v1.9.0 с Go 1.27.3 и базой уязвимостей от 21 октября 2026 года
не находит достижимых уязвимостей ни в стандартной библиотеке, ни в зависимостях.
На Go 1.27.2 была достижима GO-2026-6809 в `crypto/x509` стандартной
библиотеки, исправленная в Go 1.27.3.
До обновления Go и зависимостей проверка на Go 1.23.4 находила 49 достижимых
уязвимостей: 42 в стандартной библиотеке и 11 в модулях `golang.org/x/net`,
`golang.org/x/text`, `google.golang.org/grpc` и `github.com/jackc/pgx/v5`
(четыре уязвимости HTTP/2 затрагивают и `net/http`, и `golang.org/x/net`).
На уровне модулей остаётся только GO-2026-5932: пакет `golang.org/x/crypto/openpgp`
не поддерживается и не имеет исправления, но проект его не импортирует.
Это результат статического анализа; проверку нужно повторять после обновления
зависимостей и перед внешним развёртыванием.

## Запуск всего стека в Docker

Нужны Docker с Compose v2 и OpenSSL; Go для этого режима не нужен.
Команды выполняются из корня репозитория.

```sh
sh scripts/gen-jwt-keys.sh
docker compose -f deployments/docker-compose.yml up -d --build --wait
```

Скрипт один раз создаёт в `secrets/` пару ключей RS256 для разработки и не
перезаписывает существующий закрытый ключ. Открытый ключ всегда выводится из
закрытого: скрипт создаёт его заново вместе с новым закрытым ключом, а также
если он отсутствует или не соответствует закрытому. Вторая команда собирает четыре
Go-сервиса и локальное S3 из закреплённого исходного кода, поднимает три PostgreSQL
и Redis и ждёт healthy. Каждый сервис применяет свои миграции при старте.
Первая сборка S3 занимает несколько минут. Ограничение поддержки MinIO и порядок
работы с файлами описаны в [документации Media](docs/media/files.md).

NATS пока не используется приложением и запускается отдельно через `--profile events`.

Gateway доступен на `http://localhost:8080`; Auth и Chat открыты только внутри
сети Compose. По этому же адресу открывается [веб-клиент](#веб-клиент).
Проверка — те же запросы, что и при локальном запуске ниже:

```sh
curl --fail http://localhost:8080/health
curl --fail http://localhost:8080/ready
```

Полезные команды:

```sh
docker compose -f deployments/docker-compose.yml ps        # состояние и health
docker compose -f deployments/docker-compose.yml logs -f gateway
docker compose -f deployments/docker-compose.yml up -d --build   # пересобрать после изменений
docker compose -f deployments/docker-compose.yml down      # остановить, данные сохраняются
docker compose -f deployments/docker-compose.yml down -v   # остановить и удалить данные
```

Все порты публикуются только на `127.0.0.1`: PostgreSQL, Redis, NATS и MinIO
используют учётные данные для разработки или работают без пароля, поэтому с
других машин они недоступны. Gateway по умолчанию тоже слушает только
loopback; чтобы открыть его в сети (например, для проверки с телефона в
доверенной сети), задайте `GATEWAY_HOST_ADDR=0.0.0.0`.

Если порт на хосте занят, переопределите его переменной окружения: например,
`POSTGRES_HOST_PORT=55432 GATEWAY_HOST_PORT=18080 docker compose ... up -d`.

| Переменная | Сервис | По умолчанию |
|---|---|---|
| `GATEWAY_HOST_ADDR` | Адрес хоста для порта Gateway | 127.0.0.1 |
| `GATEWAY_HOST_PORT` | Gateway (HTTP) | 8080 |
| `POSTGRES_HOST_PORT` | PostgreSQL Auth | 5432 |
| `CHAT_POSTGRES_HOST_PORT` | PostgreSQL Chat | 5433 |
| `REDIS_HOST_PORT` | Redis | 6379 |
| `NATS_HOST_PORT`, `NATS_MONITOR_HOST_PORT` | NATS | 4222, 8222 |
| `MINIO_HOST_PORT`, `MINIO_CONSOLE_HOST_PORT` | MinIO | 9000, 9001 |

Уровни логов задаются через `AUTH_LOG_LEVEL`, `CHAT_LOG_LEVEL` и
`GATEWAY_LOG_LEVEL`, разрешённые CORS-источники — через
`GATEWAY_CORS_ALLOWED_ORIGINS`, срок жизни access token — через
`AUTH_JWT_ACCESS_TTL` (по умолчанию `15m`; для показа обновления токена удобно `2m`).
Остальная конфигурация задана в Compose-файле и совпадает с `.env.example`,
только вместо `localhost` указаны имена сервисов.

Как устроены образы:

- Один `Dockerfile` для всех сервисов: сервис выбирается аргументом сборки
  `SERVICE`, версия Go — аргументом `GO_VERSION` (по умолчанию 1.27.3; держите
  её равной строке `toolchain` в `go.mod`). Бинарники собираются статически
  (`CGO_ENABLED=0`, `-trimpath`).
- Базовые образы закреплены: сборочный — точной версией Go и Alpine
  (`golang:1.27.3-alpine3.24`), runtime — по digest. Новый digest берётся из
  `docker buildx imagetools inspect gcr.io/distroless/static-debian12:nonroot`.
- Runtime-образ — `distroless/static` без shell, запуск от непривилегированного
  пользователя (uid 65532), корневая ФС только для чтения.
- Healthcheck выполняет встроенный бинарник `cmd/healthcheck`: для Auth и Chat —
  стандартный gRPC health check, для Gateway — `GET /health`. Порядок старта:
  Chat ждёт healthy Auth и Redis, Gateway — healthy Auth, Chat и Redis.
  Redis задаёт только порядок старта Chat и не входит в его healthcheck: если
  Redis недоступен, Chat продолжает работать без событий.
- Chat публикует события в Redis сети Compose (`redis:6379`). При остановке
  Compose ждёт до 15 секунд (`stop_grace_period`): до 5 секунд на текущие
  RPC и до 5 секунд (`CHAT_EVENT_DRAIN_TIMEOUT`) на публикацию очереди событий.
- Ключи и сертификаты не попадают в образы: `.dockerignore` исключает
  `secrets/` и `.env`, а ключи JWT монтируются в Auth только для чтения в
  `/run/secrets/`. Скрипт делает файлы ключей читаемыми для пользователя
  контейнера, а каталог `secrets/` — доступным только владельцу. Если ключи
  создавались вручную на Linux, перезапустите скрипт, чтобы исправить права.
- Если запустить стек до создания ключей, на Linux `up` завершится ошибкой
  `bind source path does not exist`, а Docker Desktop создаст на месте ключей
  пустые каталоги и Auth не стартует (`is a directory`). В обоих случаях
  выполните `docker compose ... down`, `sh scripts/gen-jwt-keys.sh` (он удалит
  такие пустые каталоги) и запустите стек снова.
- Gateway в Compose работает по HTTP без TLS; для TLS смонтируйте сертификат
  так же, как ключи, и задайте `GATEWAY_TLS_CERT_PATH` и `GATEWAY_TLS_KEY_PATH`.

## Локальный запуск Auth, Chat и Gateway

Нужны Go **1.26+**, Docker с Compose и OpenSSL. Для race-тестов нужен C-компилятор.
В `go.mod` указан toolchain `go1.27.3`: при стандартном `GOTOOLCHAIN=auto` команда
`go` сама скачает и использует его, если локальная версия Go старше.
Все команды выполняются из корня репозитория.

```sh
cp .env.example .env
sh scripts/gen-jwt-keys.sh
go mod download
docker compose -f deployments/docker-compose.yml up -d postgres chat-postgres redis
```

Здесь из Compose запускается только инфраструктура. Если порт занят, задайте
`POSTGRES_HOST_PORT` и другие переменные из таблицы выше и поправьте адреса в `.env`.
Не запускайте одновременно полный стек в Docker и сервисы через `go run`:
они займут одни и те же порты.

В первом терминале загрузите переменные и запустите Auth:

```sh
set -a
. ./.env
set +a
go run ./cmd/auth
```

Во втором терминале запустите Chat:

```sh
set -a
. ./.env
set +a
go run ./cmd/chat
```

В третьем терминале аналогично запустите Gateway:

```sh
set -a
. ./.env
set +a
go run ./cmd/gateway
```

Приложения читают переменные окружения; `.env` автоматически не загружается.
По умолчанию Auth слушает `:50051`, Chat — `:50052`, Gateway — `:8080`.
Auth и Chat применяют миграции своих БД при запуске. `/ready` требует готовности
обоих gRPC-сервисов; Redis не входит в readiness из-за режима fail-open.
Chat публикует события в тот же Redis (`CHAT_REDIS_ADDR`) в фоне; если Redis
недоступен, операции выполняются без задержки, а события теряются.

```sh
curl --fail http://localhost:8080/health
curl --fail http://localhost:8080/ready
curl --fail http://localhost:8080/api/v1/auth/register \
  -H 'Content-Type: application/json' \
  -d '{"email":"demo@example.com","username":"demo_user","password":"DemoPassword123"}'
```

Этот локальный запуск обслуживает Auth API, комнаты и сообщения Chat и WebSocket-события. Для вложений запустите также `cmd/media` с настройками `MEDIA_*` из `.env.example` или используйте полный Compose-стек. Ключи и `.env` исключены из Git через `.gitignore`.

## Веб-клиент

Gateway отдаёт веб-клиент на `http://localhost:8080/`: `index.html` по `/` и
файлы клиента под `/app/`. Клиент встроен в бинарник Gateway (`web/`), поэтому
страница и API имеют один origin и CORS не нужен. Отдаются только файлы
известных типов, каталоги не перечисляются. Страница идёт с CSP без
`unsafe-inline`: выполняются только скрипты и стили клиента с того же origin.

В клиенте есть регистрация, вход и выход, список комнат по последней
активности, поиск пользователей по началу имени (от 2 символов) с открытием
личного диалога, создание каналов и переписка с подгрузкой ранних сообщений;
повтор неудачной отправки не создаёт копию сообщения. К сообщению можно
прикрепить до 5 файлов по 10 МиБ (PNG, JPEG, PDF, текст); вложения
скачиваются с токеном доступа и не открываются в странице. Панель «Участники»
показывает состав комнаты; владелец канала добавляет и удаляет участников,
остальные могут покинуть канал. Данные сервера выводятся только как текст.
Всё, что загружено для вошедшего пользователя, отбрасывается при выходе:
ответы на запросы прежнего пользователя не попадают на страницу следующего.

События приходят по WebSocket: новые сообщения, появление и исчезновение
комнат, изменения состава. Комнаты с новыми сообщениями отмечаются в списке,
индикатор в шапке показывает состояние соединения. После обрыва клиент сам
переподключается с нарастающей задержкой, а после каждого подключения
перечитывает список комнат и догружает сообщения загруженных комнат после
последнего известного номера, как требует [протокол](docs/chat/realtime.md).
Кнопка «Обновить» делает то же вручную. В открытое соединение новый токен
уходит за 90 секунд до истечения (кадры `auth` не чаще раза в 10 секунд);
после закрытия с кодом `4001` токен обновляется и соединение сразу
восстанавливается. [Сценарий демонстрации](docs/demo.md) показывает переписку,
обмен файлом, запрет доступа третьему пользователю и восстановление соединения.

Токены хранятся в `sessionStorage` вкладки: перезагрузка страницы сохраняет вход,
а каждая вкладка входит отдельно, поэтому в одном браузере можно открыть
нескольких пользователей. Не дублируйте вкладку с выполненным входом: дубликат
получает копию refresh token, и при первом обновлении Auth примет повтор за
кражу и завершит сессии обеих вкладок. Access token обновляется за минуту до
истечения и после неожиданного `401`; отклонённый refresh token завершает вход,
сетевой сбой — нет. Ответ на запрос прежней сессии (после выхода или смены
аккаунта) отбрасывается и не меняет текущую.

Клиент написан на HTML, CSS и JavaScript-модулях без сборки и сторонних
библиотек. Его логика проверяется тестами на встроенном `node:test`; нужен
Node.js 22+ (шаблоны файлов в `--test`), пакеты не устанавливаются:

```sh
node --test "web/test/*.test.mjs"
```

С адресом запущенного Gateway те же модули работают через настоящий стек:
регистрация, вход, обновление токена и выход, поиск, личный диалог с
перепиской и догрузкой, запрет доступа постороннему, управление участниками
канала, обмен файлом и запрет доступа к нему третьему пользователю и
удалённому участнику, доставка событий по WebSocket, обрыв соединения и
догрузка пропущенного. Без переменной эти тесты пропускаются:

```sh
VAULT_CHAT_WEB_GATEWAY_URL=http://127.0.0.1:8080 node --test "web/test/*.test.mjs"
```

## Доступные REST-маршруты

| Метод | Путь | Назначение |
|---|---|---|
| POST | `/api/v1/auth/register` | Регистрация |
| POST | `/api/v1/auth/login` | Вход и получение пары токенов |
| POST | `/api/v1/auth/refresh` | Ротация refresh token и новая пара токенов |
| POST | `/api/v1/auth/logout` | Завершение сессии по refresh token |
| GET | `/api/v1/auth/me` | Личность из access token |
| DELETE | `/api/v1/auth/sessions` | Отзыв всех сессий владельца access token |
| GET | `/api/v1/users` | Поиск по началу имени без учёта регистра: `query` (от 2 символов), `limit` (по умолчанию 20, максимум 50); себя не возвращает; нужен access token |
| GET | `/api/v1/users/{user_id}` | Публичный профиль существующего пользователя; нужен access token |
| GET | `/api/v1/rooms` | Комнаты вызывающего по последней активности: `cursor`, `limit` (по умолчанию 50, максимум 100) |
| POST | `/api/v1/rooms/direct` | Получение или создание диалога с существующим пользователем |
| POST | `/api/v1/rooms/channels` | Создание канала; вызывающий становится владельцем |
| GET | `/api/v1/rooms/{room_id}` | Метаданные комнаты только для её участников |
| PUT | `/api/v1/rooms/{room_id}/members/{user_id}` | Добавление существующего пользователя владельцем канала |
| GET | `/api/v1/rooms/{room_id}/members` | Состав комнаты только для участников: `cursor`, `limit` (по умолчанию 50, максимум 100) |
| DELETE | `/api/v1/rooms/{room_id}/members/{user_id}` | Удаление участника владельцем канала; повтор безопасен |
| DELETE | `/api/v1/rooms/{room_id}/members/me` | Выход из канала; владелец выйти не может, пока нет передачи владения |
| POST | `/api/v1/rooms/{room_id}/messages` | Отправка текста; повтор с тем же UUID и текстом возвращает исходное сообщение |
| GET | `/api/v1/rooms/{room_id}/messages` | История участников: `cursor`, `limit` (по умолчанию 50, максимум 100); `after` — сообщения после известного номера, от старых к новым |
| GET | `/api/v1/ws` | WebSocket с событиями комнат вызывающего; токен передаётся первым сообщением, см. [протокол](docs/chat/realtime.md) |
| GET | `/` | Веб-клиент; его файлы — под `/app/` |
| GET | `/health` | Проверка работы процесса Gateway |
| GET | `/ready` | Проверка готовности Gateway и его зависимостей |

Форматы запросов, ответы и авторизация описаны в
[OpenAPI](docs/api/gateway.yaml).

## Проверки

Все проверки запускаются одной командой; она останавливается на первой
ошибке и возвращает ненулевой код:

```sh
xmake ci
```

`xmake ci` проверяет форматирование, `go vet`, golangci-lint и сборку, затем
запускает все тесты с race detector вместе с integration-тестами PostgreSQL и
S3, проверяет покрытие пакетов `service` и `handler` (не ниже 70%), фаззит
каждую цель по 10 секунд и запускает `govulncheck`. Для integration-тестов
команда поднимает `postgres` и `minio` из Compose и создаёт отдельные тестовые
БД. Нужны xmake 2.8+, Docker и инструменты ниже; список отдельных команд — в
[CONTRIBUTING](CONTRIBUTING.md#individual-commands).

Те же проверки без xmake:

```sh
go test -race -count=1 ./...
go vet ./...
golangci-lint run
golangci-lint fmt --diff
go build ./...
govulncheck ./...
node --test "web/test/*.test.mjs"
```

golangci-lint v2 и `govulncheck` должны быть собраны Go 1.27 или новее, иначе
они не загружают пакеты проекта; golangci-lint проверен с версией v2.14.0.
`go install` выбирает toolchain по `go.mod` устанавливаемой утилиты, поэтому
версию Go для сборки `govulncheck` нужно указать явно:

```sh
GOTOOLCHAIN=go1.27.3 go install golang.org/x/vuln/cmd/govulncheck@latest
```

Без переменных тестовых БД PostgreSQL integration-тесты пропускаются.
Для полного прогона создайте две отдельные тестовые БД в запущенном PostgreSQL:

```sh
docker compose -f deployments/docker-compose.yml exec -T postgres \
  createdb -U auth vault_chat_auth_test
docker compose -f deployments/docker-compose.yml exec -T postgres \
  createdb -U auth vault_chat_chat_test

VAULT_CHAT_TEST_DATABASE_URL='postgres://auth:auth@localhost:5432/vault_chat_auth_test?sslmode=disable' \
VAULT_CHAT_TEST_CHAT_DATABASE_URL='postgres://auth:auth@localhost:5432/vault_chat_chat_test?sslmode=disable' \
  go test -race -count=1 ./...
```

Тесты очищают таблицы: используйте только отдельные тестовые БД.
Команды `createdb` нужны один раз при подготовке окружения.

Проверка запущенного Compose-стека: тест ждёт `/ready`, регистрирует двух
новых пользователей, создаёт диалог, открывает WebSocket второго и отправляет
сообщение первого через REST; второй должен получить `message.created` за
10 секунд. Тест обращается к Gateway через опубликованный порт, поэтому
проверяет и связь Chat и Gateway через общий Redis. Адрес Gateway задаётся
переменной `VAULT_CHAT_COMPOSE_GATEWAY_URL` (с учётом `GATEWAY_HOST_PORT`);
без неё тест пропускается:

```sh
docker compose -f deployments/docker-compose.yml up -d --build --wait && \
  VAULT_CHAT_COMPOSE_GATEWAY_URL=http://127.0.0.1:8080 \
  go test -tags compose -count=1 ./tests/compose/...
```

Фаззинг всех целей по 30 секунд — `xmake fuzz` (другая длительность:
`xmake fuzz -t 2m`), без xmake:

```sh
for package in $(go list ./...); do
  for target in $(go test "$package" -run '^$' -list '^Fuzz' | awk '/^Fuzz/ {print $1}'); do
    go test "$package" -run '^$' -fuzz="^${target}$" -fuzztime=30s -parallel=2 || exit 1
  done
done
```

Для работы с protobuf нужны `buf`, `protoc-gen-go` и `protoc-gen-go-grpc`:

```sh
cd api/proto
buf lint
buf generate
```
