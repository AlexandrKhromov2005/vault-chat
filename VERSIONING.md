# Версионирование Vault Chat

Версия относится ко всему приложению: Auth, Chat, Media и Gateway выпускаются
вместе из одного коммита. Первый релиз — `v0.1.0`, backend MVP. В `v0.2.0` добавлены
веб-клиент, воспроизводимое VPS-развёртывание и общая команда проверок. В `v0.3.0` добавлены метрики, закрытые дашборды и эксплуатационные алерты.
Изменения и ограничения релизов фиксируются в [CHANGELOG.md](CHANGELOG.md).

## Номера версий

Используем формат `MAJOR.MINOR.PATCH`; Git-тег содержит префикс `v`.

| Изменение | Версия |
|---|---|
| Исправление без нарушения совместимости | Увеличиваем PATCH: `v0.1.0` → `v0.1.1` |
| Законченный функциональный блок | Увеличиваем MINOR: `v0.1.0` → `v0.2.0`, PATCH обнуляем |
| Несовместимое изменение после `v1.0.0` | Увеличиваем MAJOR, MINOR и PATCH обнуляем |
| Кандидат на релиз | Добавляем суффикс: `v0.2.0-rc.1` |

До `v1.0.0` API развивается: несовместимые изменения требуют новой MINOR-версии
и отдельного описания миграции в changelog. PATCH сохраняет совместимость.
Это относится к REST, gRPC, формату WebSocket-событий и конфигурации запуска.
Изменение схемы БД требует миграции; её ограничения и порядок обновления
описываются в релизе.

`v1.0.0` выпускаем после согласования стабильного пользовательского сценария,
контрактов API и гарантий совместимости. Срок защиты сам по себе не определяет
номер версии. Отдельные версии сервисов вводим, когда понадобится независимый выпуск.

## Когда ставить тег

Тег ставим после слияния законченного блока в `main` и проверки общего стека.
Коммит или отдельный PR не требуют собственного релиза. Изменения до следующего
релиза записываем в раздел `Unreleased` changelog.

Для релиза:

1. Проверить изменения, миграции, совместимость и ограничения. Выполнить
   применимые проверки из README: unit/race, lint, vet, protobuf, build,
   govulncheck, интеграционные и Compose-тесты. Документационные изменения
   не требуют повторной сборки неизменённого приложения.
2. Выбрать версию. Перенести записи из `Unreleased` в раздел с номером и датой
   релиза, оставить пустой `Unreleased`. Включить это изменение через PR в `main`.
3. Обновить локальный `main`, убедиться в чистоте рабочего дерева и записать
   полный SHA проверенного коммита.
4. Создать аннотированный тег на этом SHA и отправить только этот тег:

   ```sh
   git tag -a v0.2.0 <проверенный-SHA> -m 'Vault Chat v0.2.0'
   git push origin refs/tags/v0.2.0
   ```

   Версия в примере заменяется на фактическую. Для кандидата используется
   тег с суффиксом `-rc.N`.
5. Создать GitHub Release для существующего тега: состав изменений, миграции,
   результат проверок и известные ограничения. Кандидат пометить как prerelease.
   Проверить, что опубликованный тег указывает на нужный коммит.

Опубликованный тег не переносим, не удаляем для повторного использования и
не перезаписываем через force push. Ошибку исправляем новым релизом. Номера
версий не дублируем в отдельном `VERSION`-файле: источник версии релиза — Git-тег.
