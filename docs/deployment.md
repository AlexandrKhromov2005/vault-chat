# VPS: установка, обновление и восстановление

Поддерживается выделенный Ubuntu 24.04 с публичным IPv4. Для небольшой группы:
2 vCPU, 4 ГБ RAM, 40–60 ГБ SSD. Это один узел MVP, без репликации и failover.
Все команды администрирования выполняются от root. Аккаунты мессенджера
создаются через «Регистрация» в браузере; Linux-пользователи им не нужны.

## Что устанавливается

`deployments/docker-compose.vps.yml` запускает четыре сервиса, три PostgreSQL,
Redis и закрытое S3. Единственный опубликованный контейнерный порт — 443.
Gateway завершает TLS 1.3 сам: IP клиента не теряется за reverse proxy.
Nginx на 80 обслуживает ACME и перенаправляет HTTP на HTTPS. Сертификат IP
выдаёт Let's Encrypt; домен не требуется. Certbot 5.8.0 проверяет обновление
каждые шесть часов и после продления перезапускает Gateway.

Каждый контейнер имеет лимит RAM, restart policy и ротацию логов 3 × 10 МБ.
Базы и Redis/S3 доступны только в Docker-сети; Redis защищён паролем.
Runtime приложения работает от UID 65532. Образы PostgreSQL/Redis закреплены
по digest; приложение использует общий неизменяемый тег образов.

Текущий MinIO — изолированное стендовое хранилище проекта. Для постоянной
эксплуатации заменить поддерживаемым S3. Внутренний gRPC пока без mTLS.
Регистрация открытая, подтверждения email нет. Firewall не заменяет защиту
провайдера от DDoS; публикация Docker-портов ограничивается самим Compose.

## Первый запуск

Использовать только выделенный сервер: installer настраивает Nginx и UFW.
Он откажется заменять чужие Nginx sites. Не копировать чужие JWT-ключи и
пароли разработки. Перед началом обновить ОС; при необходимости перезагрузить.

```sh
apt-get update
apt-get upgrade -y
apt-get install -y git docker.io docker-compose-v2 python3 openssl
systemctl enable --now docker
git clone https://github.com/AlexandrKhromov2005/vault-chat.git /opt/vault-chat
cd /opt/vault-chat
git checkout v0.2.0
# Подставить IPv4 из панели провайдера:
scripts/vps.sh init YOUR_PUBLIC_IPV4 v0.2.0
scripts/vps.sh build v0.2.0
scripts/vps.sh install
scripts/vps.sh status
```

`init` создаёт `.env.vps` с mode 600 и отдельными случайными паролями, а также
JWT-ключи. Повторный вызов сохраняет значения; другой тег меняется через
`update`. Открыть `https://YOUR_PUBLIC_IPV4/`; `/ready` должен подтвердить
Auth, Chat и Media. Для ACME нужны входящие TCP 80/443 и исходящий HTTPS;
настроить также firewall в панели провайдера. SSH остаётся на 22.
Installer не меняет пользователей Linux, SSH-ключи и пароль root.

Сборка выполняется последовательно и требует дополнительной памяти/диска.
Предпочтительно собирать на рабочей машине из того же тега, затем передать
образы через `docker save | gzip`, `scp` и `docker load`. Для закрытого
registry потребуется отдельная настройка. Если локальная сборочная сеть
не видит прокси, можно задать `VAULT_BUILD_NETWORK=host`.
Команда build откажется перезаписать существующий тег.

## Обновление

Прочитать changelog и ограничения миграций. Сначала проверить новый релиз
на отдельном стеке. Поставить актуальные scripts/Compose из нужного Git-тега
в checkout, сохранить `.env.vps` и `secrets/`, собрать/загрузить все пять образов:

```sh
cd /opt/vault-chat
git fetch origin --tags
git checkout NEW_RELEASE_TAG
scripts/vps.sh build NEW_RELEASE_TAG
scripts/vps.sh update NEW_RELEASE_TAG
```

Update проверяет наличие образов, делает полную копию, меняет только
`VAULT_IMAGE_TAG`, запускает стек с `--wait` и проверяет `/ready`.
Во время смены контейнеров возможен короткий перерыв; WebSocket переподключается.
Миграции выполняются приложением. Автоматического rollback схемы нет:
при несовместимой миграции нужен проверенный restore полного состояния.
Если обновились systemd/Nginx templates, повторить `install`.

## Backup

`vault-chat-backup.timer` запускается ежедневно в 03:30 по Москве (00:30 UTC).
`/var/backups/vault-chat` хранит примерно семь дней успешных копий:
три PostgreSQL dump, объекты S3, секреты, Compose и список образов.

Приложения и S3 кратко ставятся на паузу, БД продолжают работать. После
снятия копии контейнеры размораживаются, в том числе при ошибке dump.
Время паузы растёт с объёмом файлов. Копия считается завершённой только
при наличии `COMPLETE` формата 1 и корректного `SHA256SUMS`.
Ручной запуск и контроль:

```sh
scripts/vps.sh backup
systemctl list-timers vault-chat-backup.timer vault-certbot.timer
journalctl -u vault-chat-backup.service
```

Внешнее копирование не настроено: локальная копия не защищает от потери VPS.
Передавать полный каталог копии на отдельный сервер/хранилище по защищённому
каналу; копия содержит пароли и приватные ключи. При ежедневном расписании
плановая потеря данных может достигать суток; целевые RPO/RTO и внешний
backup требуют отдельной проверки на реальном объёме.

## Restore

Восстанавливать сначала на отдельной машине с тем же IP либо в изолированном
Docker-проекте. Не запускать `init` перед restore. Нужны свежий checkout нужного
релиза, полный каталог backup и все образы из `images.txt` (включая PostgreSQL
и Redis). Можно передать их через `docker save` / `docker load`.

```sh
cd /opt/vault-chat
scripts/vps.sh restore /path/to/complete-backup
scripts/vps.sh install
```

Restore откажется работать, если уже существуют `.env.vps`, `secrets/` или
volumes выбранного проекта. Он проверяет checksum всех файлов, запрещает
ссылки и выход архивов за каталог; затем восстанавливает три БД и S3,
поднимает стек и проверяет `/ready`. Он ничего не удаляет при отказе:
после частичного сбоя сохранять получившееся состояние для диагностики.
Перед повтором выбрать новый проект/checkout; существующие данные удалять
только после отдельной проверки и сохранения копии.

На другом IP сначала получить сертификат для нового адреса и обновить
`PUBLIC_IP`/TLS; сертификат старого IP не подходит. Для изолированных проверок
допустимы `VAULT_ROOT`, `VAULT_PROJECT`, `VAULT_BACKUP_ROOT`: указать отдельные
каталоги, проект, порты и TLS healthcheck в копии Compose. Systemd installer
намеренно работает только с `/opt/vault-chat` и стандартным проектом.

## Проверки разработки

```sh
xmake ci          # Go, integration, web, coverage, VPS, fuzz и govulncheck
xmake deployment  # только scripts/backup/Compose; без root и рабочего VPS
```

Для VPS-проверок нужны Python 3.11+, OpenSSL и Docker Compose v2.
Проверяются повторный init, права секретов, повреждение и опасные пути backup,
разморозка после ошибки, отсутствие открытых data-портов и наличие TLS.
Полное restore проверять также на реальных PostgreSQL/S3 и загруженных данных.
