# Требования и план подготовки к защите Vault Chat

Состояние на 22 октября 2026 года с учётом блока Media и вложений (#52–59)
и минимального веб-клиента (цепочка PR веб-клиента).
Реализованным считается то, что слито в `main` и проверено. Открытый PR
не закрывает требование до слияния и проверки общего стека.

## Требования курса

Основание — предоставленный командой конспект лекции и семинара 1 курса
«Безопасность высоконагруженных систем».

| Этап | Срок | Требование |
|---|---|---|
| Коллоквиум | Середина ноября 2026 | Запускаемое микросервисное приложение: несколько сервисов, БД, кэш и брокер |
| Экзамен | Вторая половина декабря 2026 | Итоговое решение с практиками ИБ и охватом всех тем курса; защита блокирующая |
| Обе защиты | Демо и опрос | Объяснить, что работает, почему работает и почему выбраны именно такие решения |

Нужно уточнить у преподавателя:

- Баллы коллоквиума: лекция указывает опрос 10 + защиту 20, семинар — демо 10 + опрос по темам 1–6 на 20.
- Достаточно ли Redis для rate limiter или требуется кэш данных приложения.
- Обязательны ли для брокера сохраняемые сообщения, очереди подписчиков и подтверждения обработки.
- Полный перечень тем 1–10, обязательные артефакты и распределение по этапам защиты.

C1/C2 в Mermaid рекомендованы в семинаре по конспекту команды. ADR, модель угроз,
нагрузочные проверки и остальные критерии ниже приняты как план проекта;
они не объявляются дополнительными прямыми требованиями преподавателя.
Media входит в собственный MVP проекта, но его обязательность для курса пока не подтверждена.

VPS-развёртывание, обновление и восстановление описаны в [инструкции](deployment.md).
Копии БД/S3/ключей проверяются checksum и восстанавливаются только в новый
проект без существующих volumes. Внешнее копирование и целевые RPO/RTO
остаются открытыми задачами.

### Выполненный блок MVP: Media

В блоке Media реализованы закрытое S3-хранилище, отдельная БД метаданных,
загрузка/скачивание через Gateway, доступ текущих участников, вложения в
сообщениях, истории и WebSocket и полный Compose-стек четырёх сервисов.
Лимиты, жизненный цикл и проверки описаны в [Media](media/files.md).
Проверены unit/race, реальные PostgreSQL и S3, полный Compose-сценарий,
фаззинг, линтер и protobuf-контракты.

Ориентир разработки — собственный MVP. Он шире функционального минимума
коллоквиума, но не закрывает автоматически требования курса к брокеру,
кэшу, обоснованиям и практикам ИБ. После Media реализован минимальный
веб-клиент для входа, комнат, переписки, вложений и событий в реальном времени.

### Кэш и брокер

- [ ] Согласовать трактовку кэша. Если требуется кэш данных, реализовать полезный сценарий, например публичные профили пользователей.
- [ ] Для кэша определить источник истины, ключи, TTL, инвалидацию и поведение при отказе; показать попадание, промах и истечение TTL.
- [ ] Согласовать гарантии брокера. Предпочтительный вариант плана — один полезный поток через NATS JetStream с сохраняемым consumer и подтверждением обработки; конкретный поток выбрать в ADR до реализации.
- [ ] Определить повторную доставку, идемпотентность, ограничения повторов и обработку неисправимых сообщений.
- [ ] Проверить: остановить consumer, опубликовать событие, запустить consumer и получить событие; повтор не должен повторять побочный эффект.
- [ ] Если событие обязано соответствовать записи в БД, определить восстановление после сбоя между commit и publish, например через transactional outbox.

Redis Pub/Sub можно сохранить для оперативной доставки в WebSocket. Он не
сохраняет пропущенные события. Catch-up восстанавливает сообщения из PostgreSQL,
но не является очередью с подтверждениями и не воспроизводит все membership-события.
Если выбран только Pub/Sub, закрытие требования о брокере зависит от согласования
преподавателем.

## План к экзамену

Рабочий план необходимо сопоставить со всеми темами курса. Отметка
«запланировано» не закрывает тему на защите.

| Направление | Критерий готовности |
|---|---|
| HTTPS и mTLS | Стенд использует HTTPS; внутренние RPC проверяют доверенный CA и идентичность сервиса; чужой сертификат отклоняется; ротация описана |
| Авторизация | Проверены вызовы без токена, с чужой идентичностью и после удаления из комнаты; срок действия access token и открытых WebSocket явно описан |
| Реплики и балансировка | Минимум две реплики Gateway за балансировщиком; проверены общий rate limit, доставка между экземплярами и reconnect при остановке одной реплики |
| Edge-защита | Ограничены частота, соединения, тело и таймауты; доверенные proxy настроены без подделки IP; выбранные WAF-правила проверены отдельно |
| DDoS | Определены модель атаки и границы защиты приложения; внешний механизм защиты канала выбран, если требуется курсом; один nginx rate limit не считается полной DDoS-защитой |
| Наблюдаемость | Метрики задержек, ошибок, RPC, WebSocket, Redis и брокера; дашборд и проверенный алерт; секретов в логах и labels нет |
| Нагрузка | Зафиксированы среда, профиль и целевая нагрузка; измерены throughput, p95/p99, ошибки и ресурсы; показаны результаты и узкое место |
| Отказы | Проверены остановка сервиса, Redis и consumer, ограниченность очередей, восстановление соединений и повторная обработка |
| Данные и секреты | Раздельные права сервисов, минимальные права runtime-пользователей БД, ограниченная внешняя доступность хранилищ; ротация ключей описана и проверена |
| Backup и restore | Backup восстановлен в отдельную БД; проверена целостность, определены допустимая потеря данных и время восстановления |
| Автоматизация | Одна команда выполняет format, vet, lint, unit/race, PostgreSQL integration, fuzz, coverage, build, govulncheck; ошибки дают ненулевой код выхода |
| Media и вложения | В рамках MVP: загрузка/скачивание, лимиты, проверка содержимого и доступа, закрытое хранилище; необходимость для курса уточняется |

Согласно CONTRIBUTING проверки выполняются локально командой `xmake ci`. Наличие
`.github` само по себе не является критерием готовности. Облачный CI вводится
отдельным решением, если потребуется.

## Проверка внешнего ревью от 24 октября 2026

Ревью PDF относится к коммиту `3ec755e`. Ниже — результат сопоставления с
кодом; расчёт памяти в PDF не является измерением реального OOM. Исправления
проверяются тестами, а оставшиеся решения требуют отдельных изменений.

| № | Оценка и результат |
|---|---|
| 1 | Подтверждено: не было общей границы параллельных Argon2-вызовов. Теперь Auth допускает две операции с паролями, остальные сразу получают `503`; регистрация и фиктивная проверка неизвестного email используют тот же пул. При штатных параметрах одновременно вычисляются не более двух хэшей по 64 МиБ; это граница работы Argon2, а не всего RSS процесса. |
| 2 | Подтверждено. Имена новых загрузок проверяются на управляющие и format-символы, включая bidi; двоеточия и конечная точка тоже запрещены. Расширение в upload/metadata/download соответствует определённому по содержимому типу. Например, текстовый `Инструкция.js` становится `Инструкция.js.txt`. Старые записи защищены при чтении без изменения самих файлов. |
| 3 | Подтверждено. Вход и регистрация получили отдельную общую квоту на IP/IPv6 /64: по умолчанию 5 запросов в минуту, burst 5. Redis обязателен для этих двух маршрутов; дополнительный локальный лимитер не позволяет сбросить квоту вытеснением Redis-ключа. В Auth есть квота на email без учёта регистра, одинаковая для существующих и неизвестных аккаунтов: burst 5, восстановление одной попытки в минуту. Обычный API по-прежнему допускает запросы при отказе Redis. |
| 4 | Подтверждено, остаётся открытым. Регистрация раскрывает занятость email, а каталог доступен любому зарегистрированному пользователю. Одинаковое сообщение об ошибке недостаточно: успешная регистрация выдаёт профиль, после чего можно проверить вход. Нужен согласованный сценарий приглашения/подтверждения email или закрытой регистрации с изменением контракта API и клиента. |
| 5 | Подтверждено. Добавлена миграция `0004_username_casefold_unique`: уникальный индекс по `lower(username)`. Она сохраняет написание имени и не переименовывает аккаунты автоматически. При существующих коллизиях миграция откатывается и запуск Auth останавливается до их разрешения. |
| 6 | Подтверждено. Gateway сохраняет общую границу восьми загрузок для защиты ресурсов, но одному пользователю выделяет не больше двух. Превышение личной квоты возвращает `429`, общего пула — `503`; все пути завершения освобождают слоты. Несколько аккаунтов всё ещё могут исчерпать общий пул. |
| 7 | Подтверждено, остаётся открытым: у файлов общий бюджет Gateway 10 секунд, поверх него серверные deadlines, а у Media свой бюджет 30 секунд. Следующее изменение должно согласованно ввести файловый бюджет и таймаут отсутствия прогресса для HTTP, gRPC и внешнего proxy. Простое увеличение общего таймаута ухудшит остальные маршруты. |
| 8 | Подтверждено как ограничение текущей модели сессий: отзыв refresh-сессий не отзывает выданные access JWT; WebSocket ограничен сроком токена. Немедленный отзыв требует привязки access к сессии/версии пользователя и закрытия активных соединений, включая другие Gateway. Это отдельное изменение протокола и хранения. |

Запись сообщения затем повторно проверяет членство отправителя под блокировкой комнаты (`lockMemberRoom`). Удаление участника между проверками не позволяет отправить сообщение. При появлении удаления или изменения метаданных файлов эту границу надо пересмотреть. |

Защитные таблицы в памяти ограничены 4096 ключами на экземпляр. Активные
квоты не вытесняются: при заполнении отклоняются новые ключи, пока полностью
восстановившиеся квоты не освободят место. Перезапуск процесса сбрасывает
локальные квоты. Квота по email действует на один Auth; перед его горизонтальным
масштабированием её нужно перенести в общее надёжное хранилище. Пользователь
за NAT или IPv6 /64 делит IP-квоту с другими пользователями этой сети.

Отдельная квота Gateway настраивается через
`GATEWAY_AUTH_RATE_LIMIT_PER_MINUTE` и `GATEWAY_AUTH_RATE_LIMIT_BURST` в обоих
Compose-файлах. Значения для тестов и нагрузочного стенда следует повышать
явно; увеличение общей `GATEWAY_RATE_LIMIT_*` её не меняет. Для большого числа
пользователей за одним proxy также нужно согласовать доверенный источник
клиентского IP: произвольные `X-Forwarded-For` не принимаются.

Перед обновлением существующей Auth БД проверить коллизии:

```sql
SELECT lower(username) AS name, array_agg(username ORDER BY username) AS usernames
FROM users
GROUP BY lower(username)
HAVING count(*) > 1;
```

Коллизии разрешаются с владельцами аккаунтов до применения миграции. Если
увеличивать `AUTH_ARGON2_MEMORY_KIB`, нужно пересчитать бюджет памяти процесса
и лимит контейнера с учётом двух одновременных операций и сборщика мусора.

Проверки изменений: все Go-тесты с race detector и отдельными PostgreSQL БД
Auth/Chat/Media; 170 веб-тестов (10 сценариев с живым Gateway пропущены);
сборка, vet, golangci-lint, deployment-проверки и фаззинг имён файлов/IP.
`govulncheck` не нашёл достижимых уязвимостей; предупреждение на уровне
`golang.org/x/crypto` относится к неимпортируемому пакету OpenPGP. Полный
Compose-стек и S3 integration в этом прогоне не запускались.

Приоритет оставшейся работы: закрытая регистрация/приглашения и минимальные
права хранилищ, затем файловые таймауты, мгновенный отзыв access-сессий,
сегментация сетей и внешние зашифрованные резервные копии.
