# Требования и план подготовки к защите Vault Chat

Состояние на 16 октября 2026 года, базовая версия `main` — `7da51b6`.
Реализованным считается то, что слито в `main` и проверено. Открытый PR
не закрывает требование до слияния и проверки общего стека.

## Требования курса

Основание — предоставленный командой конспект лекции и семинара 1 курса
«Безопасность высоконагруженных систем».

| Этап | Срок | Требование |
|---|---|---|
| Коллоквиум | Середина ноября 2026 | Запускаемое микросервисное приложение: несколько сервисов, БД, кэш и брокер |
| Экзамен | Вторая половина декабря 2026 | Итоговое решение с практиками ИБ и охватом всех тем курса; защита блокирующая |
| Обе защиты | Демо и опрос | Объяснить, что работает, почему работает и почему выбраны именно такие решения |

Нужно уточнить у преподавателя:

- Баллы коллоквиума: лекция указывает опрос 10 + защиту 20, семинар — демо 10 + опрос по темам 1–6 на 20.
- Достаточно ли Redis для rate limiter или требуется кэш данных приложения.
- Обязательны ли для брокера сохраняемые сообщения, очереди подписчиков и подтверждения обработки.
- Полный перечень тем 1–10, обязательные артефакты и распределение по этапам защиты.

C1/C2 в Mermaid рекомендованы в семинаре по конспекту команды. ADR, модель угроз,
нагрузочные проверки и остальные критерии ниже приняты как план проекта;
они не объявляются дополнительными прямыми требованиями преподавателя.
Media входит в собственный MVP проекта, но его обязательность для курса пока не подтверждена.

## План до коллоквиума

### Запуск и демонстрация

- [ ] Исправить замечания review, разбить крупные PR и слить необходимые изменения.
- [ ] Запускать сервисы, БД, Redis и используемый брокер одной командой после документированной подготовки ключей.
- [ ] Объединить Compose и real-time: `CHAT_REDIS_ADDR=redis:6379`, параметры `CHAT_EVENT_*` и `GATEWAY_WS_*`; для Chat установить `stop_grace_period` не менее 15 секунд.
- [ ] Определить порядок запуска и поведение при отказе Redis; `depends_on` не заменяет восстановление соединения после отказа.
- [ ] Подготовить demo-скрипт или минимальный клиент: регистрация/вход, диалог, обмен в реальном времени, запрет доступа третьему пользователю.
- [ ] Показать reconnect и catch-up сообщений; список комнат и membership пересинхронизировать отдельно.
- [ ] Повторить запуск на чистом окружении по инструкции; `/ready` должен подтверждать заявленные зависимости.

### Кэш и брокер

- [ ] Согласовать трактовку кэша. Если требуется кэш данных, реализовать полезный сценарий, например публичные профили пользователей.
- [ ] Для кэша определить источник истины, ключи, TTL, инвалидацию и поведение при отказе; показать попадание, промах и истечение TTL.
- [ ] Согласовать гарантии брокера. Предпочтительный вариант плана — один полезный поток через NATS JetStream с сохраняемым consumer и подтверждением обработки; конкретный поток выбрать в ADR до реализации.
- [ ] Определить повторную доставку, идемпотентность, ограничения повторов и обработку неисправимых сообщений.
- [ ] Проверить: остановить consumer, опубликовать событие, запустить consumer и получить событие; повтор не должен повторять побочный эффект.
- [ ] Если событие обязано соответствовать записи в БД, определить восстановление после сбоя между commit и publish, например через transactional outbox.

Redis Pub/Sub можно сохранить для оперативной доставки в WebSocket. Он не
сохраняет пропущенные события. Catch-up восстанавливает сообщения из PostgreSQL,
но не является очередью с подтверждениями и не воспроизводит все membership-события.
Если выбран только Pub/Sub, закрытие требования о брокере зависит от согласования
преподавателем.

## План к экзамену

Рабочий план необходимо сопоставить со всеми темами курса. Отметка
«запланировано» не закрывает тему на защите.

| Направление | Критерий готовности |
|---|---|
| HTTPS и mTLS | Стенд использует HTTPS; внутренние RPC проверяют доверенный CA и идентичность сервиса; чужой сертификат отклоняется; ротация описана |
| Авторизация | Проверены вызовы без токена, с чужой идентичностью и после удаления из комнаты; срок действия access token и открытых WebSocket явно описан |
| Реплики и балансировка | Минимум две реплики Gateway за балансировщиком; проверены общий rate limit, доставка между экземплярами и reconnect при остановке одной реплики |
| Edge-защита | Ограничены частота, соединения, тело и таймауты; доверенные proxy настроены без подделки IP; выбранные WAF-правила проверены отдельно |
| DDoS | Определены модель атаки и границы защиты приложения; внешний механизм защиты канала выбран, если требуется курсом; один nginx rate limit не считается полной DDoS-защитой |
| Наблюдаемость | Метрики задержек, ошибок, RPC, WebSocket, Redis и брокера; дашборд и проверенный алерт; секретов в логах и labels нет |
| Нагрузка | Зафиксированы среда, профиль и целевая нагрузка; измерены throughput, p95/p99, ошибки и ресурсы; показаны результаты и узкое место |
| Отказы | Проверены остановка сервиса, Redis и consumer, ограниченность очередей, восстановление соединений и повторная обработка |
| Данные и секреты | Раздельные права сервисов, минимальные права runtime-пользователей БД, ограниченная внешняя доступность хранилищ; ротация ключей описана и проверена |
| Backup и restore | Backup восстановлен в отдельную БД; проверена целостность, определены допустимая потеря данных и время восстановления |
| Автоматизация | Одна команда выполняет format, vet, lint, unit/race, PostgreSQL integration, fuzz, coverage, build, govulncheck; ошибки дают ненулевой код выхода |
| Media и вложения | В рамках MVP: загрузка/скачивание, лимиты, проверка содержимого и доступа, закрытое хранилище; необходимость для курса уточняется |

Согласно CONTRIBUTING проверки пока планируются локально. Нужен работающий
`xmake ci` либо согласованный эквивалент с обновлением регламента. Наличие
`.github` само по себе не является критерием готовности. Облачный CI вводится
отдельным решением, если потребуется.

### Матрица покрытия курса

- [ ] Получить точные названия тем 1–10 и критерии оценивания.
- [ ] Для каждой темы заполнить строку: тема → механизм проекта → статус → тест или demo → ADR или обоснование.
- [ ] Отметить темы 1–6 для коллоквиума и проверить покрытие всех тем к экзамену.
- [ ] Для каждой обязательной строки приложить воспроизводимую команду и ожидаемый результат.

TOTP, E2EE, организации, расширенный RBAC, Kubernetes и service mesh остаются
дальнейшим развитием, пока их необходимость не подтверждена темами курса
или отдельным решением команды.
