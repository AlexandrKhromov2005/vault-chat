# Android-клиент: план

Рабочий план, а не спецификация. Описывает направление и границы; детали
уточняются исследованием на каждом этапе. Ветка приложения —
`feature/android-app`, код клиента — в каталоге `android/` этого же репозитория.
Правки бэкенда идут отдельными PR в `main`, ветка приложения подтягивает их
rebase.

Пометки:

- **[проверить]** — факт взят из обзоров или новостей и не подтверждён на
  устройстве или в документации; перед тем как на него опираться, проверить.
- **[решить]** — открытый вопрос, решение принимает команда.
- **[сделано]** / **[на ревью]** — состояние этапа или правки бэкенда.

## 1. Цель и рамки

- Надёжный Android-клиент Vault Chat: переживает плохую мобильную сеть, смену
  Wi-Fi/LTE, убийство процесса и недоставленные push без потери сообщений и без
  разлогина.
- Быстрый: холодный старт и открытие чата без заметной задержки, плавная
  прокрутка длинной истории.
- iOS не делаем. Kotlin Multiplatform не нужен.
- Распространение — только подписанный APK в GitHub Releases. Google Play,
  RuStore и другие сторы не используем.
- Функционально — паритет с веб-клиентом (`web/`): вход и регистрация по
  приглашению, комнаты, диалоги, каналы, участники, сообщения с догрузкой,
  вложения, события в реальном времени. Новые возможности — после паритета.

## 2. Решение: нативный Kotlin + Jetpack Compose

Рассмотренные варианты:

| Вариант | Почему не он |
|---|---|
| PWA | Push только через Web Push поверх FCM; без Google Play Services не ставится как WebAPK и, по всей видимости, не получает push **[проверить]**; WebSocket в фоне быстро замораживается |
| TWA (Bubblewrap) | Push всё равно идёт через Chrome/FCM, остаются все проблемы PWA |
| Capacitor | Сложное (push, фон, Keystore) всё равно пишется на Kotlin; WebView ничего не даёт в скорости; экономится только UI, а это самая простая часть |
| Flutter / React Native | Новый язык плюс плагины в самых хрупких местах (фон, push, хранилище) |
| gomobile для протокола | Мост только для простых типов, не стыкуется с корутинами и Flow, отладка через NDK; логика переподключения на Kotlin дешевле моста |

Почему Kotlin: прямой доступ к WorkManager, Keystore, OkHttp, Room и
уведомлениям без мостов; лучшая производительность; корутины и каналы близки
Go-разработчикам; Android Studio полноценно работает на Windows.

Веб-клиент остаётся как есть. Манифест и service worker для него можно
добавить отдельно, если будет время, но это не основной клиент.

## 3. Архитектура клиента

Направление — offline-first с единственным источником истины в локальной БД.

- **UI (Compose)** читает только из Room через Flow и ничего не знает о сети.
- **Репозитории** пишут в Room ответы REST и события WebSocket.
- **Sync engine** — отдельный компонент, который:
  - держит WebSocket, пока приложение на экране;
  - после каждого `ready` перечитывает список комнат и догружает
    `?after=<последний sequence>` для известных комнат (как веб-клиент, см.
    `docs/chat/realtime.md`);
  - видит дыру в `sequence` и догружает пропущенное;
  - переподключается с нарастающей задержкой и джиттером, реагирует на смену
    сети (`ConnectivityManager`);
  - ведёт исходящую очередь: сообщение сначала пишется в Room со статусом
    «отправляется» и `client_message_id`, повтор отправки идемпотентен на
    сервере.
- **Фоновая синхронизация** — WorkManager (expedited work по push, периодическая
  работа как подстраховка).

Модули Gradle — пока один модуль `:app` с пакетами `core/` и `ui/`; делить,
когда появится причина. DI — ручная сборка зависимостей в `AppContainer`
(решено на этапе 2): без кодогенерации и с быстрой сборкой.

Предварительный набор библиотек (версии выбрать на старте, свежие стабильные):

- Compose BOM, Material 3, Navigation Compose, Lifecycle/ViewModel;
- OkHttp (REST и WebSocket), Retrofit, kotlinx.serialization (решено на
  этапе 2);
- Room + Paging 3;
- Android Keystore напрямую для секретов (см. раздел 5);
- WorkManager;
- Coil для изображений (с заголовком авторизации).

Генерация клиента из `docs/api/gateway.yaml` через openapi-generator
(`kotlin`, kotlinx.serialization, корутины) **[проверить]** качество
сгенерированного кода; если оно плохое — ручной тонкий клиент по спецификации
и тест, сверяющий его со спецификацией.

## 4. Сеть и протокол

- REST и WebSocket к Gateway по HTTPS/WSS. Cleartext запрещён в release через
  network security config; в debug разрешён только локальный адрес эмулятора.
- WebSocket: первый кадр `{"type":"auth","token":...}`, ответ `ready` с
  `expires_at`; новый `auth` до истечения (не чаще раза в 10 с); закрытие 4001 —
  обновить токен и сразу переподключиться. Неизвестные типы событий и поля
  игнорировать.
- Таймауты, ping, обработка 429/503 с `Retry-After` — по документации Gateway.
- Сервер: текущий VPS доступен по IP с сертификатом Let's Encrypt на IP-адрес.
  Такой сертификат короткоживущий (около 6 дней), цепочка
  `YE2 → Root YE → ISRG Root X2`. Сервер отдаёт и кросс-подпись ISRG Root X2
  от ISRG Root X1, а X1 есть в системном хранилище с Android 7.1.1, поэтому
  при minSdk 26 своих trust anchors не добавляем. Проверить вход на эмуляторе
  API 26 **[проверить]**. Адрес сервера — поле на экране входа; значение по
  умолчанию задаётся при сборке (`vaultchat.defaultServer` вне репозитория,
  в debug — `http://10.0.2.2:8080`).
- Certificate pinning: лист и промежуточный сертификат меняются каждые
  несколько дней, поэтому их не пинить. Если пинить, то только корни, с
  запасным вариантом **[решить]**; обновления APK ручные, ошибка пиннинга
  означает неработающее приложение до обновления.

## 5. Сессия и токены

- Access token — только в памяти.
- Refresh token — в зашифрованном хранилище с ключом в Android Keystore.
  `security-crypto` (EncryptedSharedPreferences) объявлена deprecated. Решено
  на этапе 2: AES-256-GCM с ключом, созданным в Keystore, и один файл в
  `noBackupFilesDir` с атомарной заменой. Tink не нужен для одного файла и
  добавляет зависимость; нечитаемый файл удаляется вместе с ключом, и
  пользователь входит заново.
- Хранилище токенов и БД исключить из резервного копирования и переноса между
  устройствами.
- Обновление токена строго одно в момент времени (Mutex): параллельные refresh
  со старым токеном сервер сейчас принимает за кражу и отзывает все сессии
  пользователя. Плюс правка бэкенда из раздела 9.1. Начатый refresh
  доводится до конца и сохраняется, даже если вызвавший экран закрыт; срок
  жизни access token отсчитывается от заголовка `Date` ответа, чтобы неверные
  часы телефона не ломали обновление.
- Исход refresh может быть неизвестен: ответ потерян, 5xx от Gateway, нечитаемое
  тело, процесс убит, диск полон. Перед отправкой сессия на диске помечается
  «refresh начат»; тот же токен повторяется сразу один раз и при следующих
  запросах, но только если попытка гарантированно дойдёт до Auth в пределах
  25 с от метки (у Auth окно 30 с, PR #108): старт не позже 15 с, таймаут
  refresh 10 с. Позже токен в refresh не предъявляется: клиент вызывает logout
  (отзыв семьи без reuse detection) и разлогинивает только это устройство.
  Окно меряется по `elapsedRealtime`, чтобы перевод часов назад его не
  продлевал; после перезапуска — по настенным часам, метка «из будущего»
  считается истёкшей. Сбой до того, как запрос начал уходить с устройства
  (нет сети, таймаут соединения), и отказ самого Gateway (4xx вроде 429)
  сессию сохраняют. 503 считается неизвестным исходом: для refresh это gRPC
  Unavailable, и Auth мог успеть закоммитить. При долгой недоступности Auth
  устройство, которому был нужен refresh, выйдет из аккаунта **[решить]**,
  устраивает ли это. Клиент рассчитан на сервер с PR #108: без окна повтор
  после потерянного ответа отзывает все сессии. Поэтому релиз APK и вход на
  стенд реальными аккаунтами — только после развёртывания #108 на этом стенде
  (на 2026-10-27 не развёрнут); до того — только тестовые аккаунты.
- Отложено: если между перезапусками процесса настенные часы шагнули назад
  меньше, чем длился перерыв, возраст метки занижается и повтор возможен за
  пределами окна. Закрывается хранением `elapsedRealtime` и
  `Settings.Global.BOOT_COUNT` рядом с меткой (в той же загрузке брать разницу
  `elapsedRealtime`).
- Logout и отзыв сессии стирают токены, локальную БД, кэш вложений и
  уведомления.
- Разлогин только при явном отказе Auth; сетевой сбой при refresh разлогином не
  считается.

## 6. Фон и уведомления

Главный принцип: **push — только сигнал «есть новое», а не транспорт.**
Надёжность не должна зависеть от доставки push.

- В push нет текста сообщения и имён — только сигнал синхронизации (возможно,
  `room_id`). По нему приложение запускает синхронизацию, догружает сообщения и
  само показывает уведомление.
- Транспорт по умолчанию — FCM. Нужен проект Firebase; публикация в Google Play
  для этого не требуется **[проверить]**. По новостям 2026 года доставка FCM в
  России местами деградировала без VPN **[проверить]**, поэтому FCM — ускорение,
  а не гарантия.
- RuStore Push без публикации в RuStore, скорее всего, недоступен: нужен проект
  в консоли RuStore и установленное приложение-дистрибьютор **[проверить]**.
  Пока не планируем.
- Запасной режим «постоянное соединение»: foreground service с WebSocket и
  постоянным уведомлением, включается пользователем. Так как Play не
  используется, его правила о типах foreground service нас не ограничивают, но
  ограничения самой ОС (Android 14–16: типы FGS, таймауты `dataSync`, запуск из
  фона) остаются **[проверить]** подходящий тип.
- UnifiedPush через свой ntfy — возможная альтернатива FCM для устройств без
  Google Play Services **[решить]** после первого релиза.
- Подстраховка без push: догрузка при каждом открытии приложения и
  периодическая работа WorkManager (частоту и реальное поведение под Doze и
  агрессивными прошивками проверить на устройствах, см. dontkillmyapp.com).
- Разрешение `POST_NOTIFICATIONS` (Android 13+) запрашивать по смыслу, а не
  при первом запуске. Каналы уведомлений: личные сообщения, каналы, служебные.

## 7. Вложения

- Лимиты как на сервере: до 5 файлов по 10 МиБ, типы PNG, JPEG, PDF, текст.
- Выбор файлов через системный Photo Picker и SAF, без разрешений на хранилище.
- Загрузка с прогрессом, отменой и повтором; большие загрузки — через
  WorkManager, чтобы пережить сворачивание.
- Скачивание с токеном доступа в приватный кэш приложения; открытие через
  `FileProvider` с временным разрешением. Изображения — превью через Coil.
- Кэш вложений ограничен по размеру и очищается при выходе.

## 8. Интерфейс

Ориентир — современные мессенджеры (Signal, Telegram), а не шаблон
«AI-сгенерированного» приложения. Принципы:

- Material 3 как основа, но своя сдержанная тема: один акцентный цвет, нейтральные
  поверхности, светлая и тёмная тема. Dynamic color (Material You) —
  **[решить]**: удобно, но размывает узнаваемость.
- Edge-to-edge, корректная работа с клавиатурой (`imePadding`), predictive back.
- Плотная, читаемая типографика; иерархия создаётся размером и насыщенностью
  шрифта, а не рамками и карточками.
- Анимации короткие и функциональные: появление сообщения, смена состояния
  отправки, переходы между экранами. Без декоративного движения.
- Состояния — честные и тихие: индикатор соединения в шапке, статус отправки у
  сообщения, понятная ошибка с действием «Повторить».

Чего не делать (признаки «нейрослопа»):

- градиентов на фоне и кнопках, glassmorphism, неоновых свечений;
- эмодзи в заголовках и пустых состояниях, сгенерированных иллюстраций;
- карточек с тенями вокруг каждого элемента, лишних скруглений;
- маркетинговых текстов вида «Добро пожаловать в будущее общения»;
- онбординга из нескольких экранов там, где хватает одного поля.

Перед реализацией — набросать ключевые экраны (список комнат, чат, вход,
участники) и согласовать в команде; Figma — по желанию.

Доступность: контраст, масштабирование шрифта, описания для TalkBack, области
нажатия не меньше 48 dp.

## 9. Правки бэкенда

Каждая — отдельный PR в `main` по правилам `AGENTS.md` (сначала регрессионный
тест, который воспроизводит дефект). Нужны независимо от клиента; веб-клиенту
тоже полезны.

1. **Идемпотентный refresh (критично, первым).** **[на ревью]** PR #108:
   повтор того же токена в течение 30 с после ротации отдаёт новую пару для
   уже созданной сессии-преемника, если преемник ещё не использован для
   refresh; новых сессий не создаётся. Повтор после использования
   преемника, более старого токена, после окна или после logout — как
   раньше, отзыв всех сессий (или отказ). Окно —
   `service.DefaultRefreshRetryWindow`. Клиенту всё равно нужен Mutex на
   refresh: окно страхует от потерянного ответа, а не от гонок между
   разными токенами. Исходная постановка: сейчас повтор уже
   использованного refresh token отзывает все сессии пользователя
   (`internal/auth/service/session.go`, `handleTokenReuse`). На мобильной сети
   ответ на `/auth/refresh` регулярно теряется, и повтор разлогинит пользователя
   везде. Направление: короткое окно (порядка 10–30 с), в котором повтор того же
   токена возвращает уже выданную пару, а не считается кражей. Исследовать, как
   это сделано у других (grace period в OAuth-серверах), и как не ослабить
   обнаружение кражи: окно короткое, ответ только тем же данным, повтор вне окна
   по-прежнему отзывает семью.
2. **Устройства и push-токены.** Таблица в Auth (или отдельный сервис
   уведомлений **[решить]**): push-токен привязан к сессии; удаляется при logout,
   отзыве сессии и ответах провайдера «токен недействителен». REST для
   регистрации и снятия токена.
3. **Отправка push.** Подписчик событий `message.created` (через тот же Redis
   Pub/Sub или будущий брокер) отправляет получателям сигнал синхронизации через
   интерфейс `PushProvider`; первая реализация — FCM HTTP v1 (Firebase Admin Go
   SDK **[проверить]** актуальность). Без текста сообщения. Схлопывание частых
   сигналов, чтобы не слать push на каждое сообщение в активном чате.
   Не слать push, если у пользователя открыт WebSocket **[решить]**.
4. **Лимиты по IP.** Вход и регистрация — 5 в минуту на IP. За NAT мобильного
   оператора и университетского Wi-Fi много пользователей делят один IP.
   Пересмотреть ключи лимита (IP + логин, отдельные лимиты для refresh)
   **[решить]**.
5. **Мелочи, выяснить по ходу.** WebSocket без `Origin` уже принимается — для
   нативного клиента подходит. Лимит 5 WebSocket на пользователя — хватает
   (телефон + веб). Проверить, что ошибки API однородны и машинно читаемы для
   клиента.

## 10. Сборка и распространение

- Gradle wrapper в `android/`; цели сборки и тестов подключить к `xmake`, чтобы
  локальная проверка оставалась одной командой **[решить]** объём.
- Release — R8 и Baseline Profiles. minSdk 26 (Android 8.0, решено на этапе 2),
  targetSdk и compileSdk — 37. Application ID —
  `io.github.alexandrkhromov2005.vaultchat`; как и ключ подписи, не меняется
  никогда.
- Подпись: один ключ на всё время жизни приложения, иначе обновление поверх не
  установится. Ключ и пароли — вне репозитория; продумать, у кого хранится и как
  резервируется.
- Публикация: APK в GitHub Releases с SHA-256 суммой и отпечатком сертификата
  подписи в описании релиза. Сборка APK локально, как и остальная проверка, —
  облачных раннеров в проекте нет **[решить]**, нужен ли CI для релизов.
- Обновления: приложение проверяет последний релиз через GitHub API и
  предлагает скачать; установка — через системный установщик (разрешение
  «установка из неизвестных источников»). Сверять подпись нового APK с текущей
  **[проверить]** как это делает система и нужно ли что-то сверх неё.
- Верификация разработчиков Android: Google вводит обязательную верификацию для
  установки APK вне сторов (часть стран с осени 2026, глобально обещают в 2027)
  **[проверить]** сроки и требования, в том числе бесплатный вариант для
  студентов и ограниченного числа устройств.
- Версия: как связать версию APK с тегами бэкенда по `VERSIONING.md` — общий
  тег или отдельная схема вроде `android-v0.1.0` **[решить]**.

## 11. Тестирование

- Unit-тесты логики (sync engine, разбор событий, очередь отправки, refresh с
  Mutex) на JVM с фейковыми часами и сетью.
- Тесты Room-миграций с первого релиза.
- Протокольные тесты против MockWebServer: обрывы, дыры в `sequence`, 4001,
  повторы, медленный сервер.
- Compose UI-тесты для ключевых сценариев.
- Интеграционный прогон против локального Compose-стека на эмуляторе
  (сценарий из `docs/demo.md`).
- Ручная проверка на реальных устройствах разных производителей: Doze,
  убийство процесса, смена сети, режим полёта, низкая память.

## 13. Риски

| Риск | Что делаем |
|---|---|
| Push не доходит (FCM в России, прошивки без GMS, энергосбережение) | Push — только ускорение; догрузка при открытии; режим постоянного соединения |
| Разлогин на плохой сети из-за reuse detection | Mutex на клиенте, идемпотентный refresh на сервере |
| Старые Android не доверяют цепочке Let's Encrypt (ISRG Root X2) | Проверить на эмуляторах minSdk; при необходимости свои trust anchors |
| Потеря ключа подписи | Резервная копия ключа вне репозитория, процедура описана |
| Верификация разработчика Android для установки APK | Отслеживать сроки, заранее выяснить бесплатный вариант |
| Кривая обучения Kotlin и Compose | Начать с каркаса и чтения, держать архитектуру простой |
| Расхождение клиента со спецификацией API | Генерация или сверка с `gateway.yaml` в тестах |
