# Нагрузочная приёмка Chat/Web

Воспроизводимая проверка того, сколько переписки выдерживает стенд с
конфигурацией VPS. Генератор работает так же, как веб-клиент: через Gateway
по TLS, с WebSocket и догрузкой после разрывов. Нагрузка Calls проверяется
отдельно (`xmake calls-load`, [calls/README.md](../../calls/README.md)).

```sh
xmake chat-load            # или: python3 tests/load/chat_load.py [--report PATH]
```

Нужны локальный Docker с Unix-сокетом и не меньше 6 CPU: CPU 0–1 отданы стенду,
2–5 — генератору. Команда собирает образы текущего checkout, поднимает
одноразовый проект Compose, выполняет прогрев, три серии, фазу переподключения и
ступени нагрузки, сохраняет отчёт JSON (по умолчанию
`build/load/chat-load-<время UTC>.json`) и удаляет всё, что создала: контейнеры,
тома, сети и образы с тегом прогона. С закэшированными слоями прогон идёт около
16 минут. В `xmake ci` он не входит; CI проверяет генератор интеграционным
тестом `TestChatLoadGeneratorRunsAProfileEndToEnd` на стеке внутри процесса.

Код выхода: `0` — все пороги выполнены, `3` — нарушен порог (нарушения есть в
отчёте и в stderr), `1` — прогон не завершился.

## Стенд

| Параметр | Значение |
|---|---|
| Конфигурация | `deployments/docker-compose.vps.yml` + `tests/load/stack.yml` |
| CPU | Весь стенд на двух CPU (`cpuset 0,1`), как 2 vCPU VPS ([deployment.md](../deployment.md)) |
| Память | Лимиты контейнеров из VPS-конфигурации: Auth 512 МиБ, Chat и Gateway по 256 МиБ, каждая PostgreSQL 384 МиБ, Redis 128 МиБ |
| Генератор | Отдельный контейнер `loadgen` на CPU 2–5, 512 МиБ; в сетях `edge` и внутренней `load-metrics`, без доступа к БД, Redis и Docker |
| Машина эталонного прогона | Docker Desktop 29.1.3 на WSL2 (ядро 6.18), 8 CPU, 3,8 ГиБ памяти VM; Compose 5.0 |

Overlay сохраняет конфигурацию VPS: mTLS между сервисами, TLS 1.3 на Gateway,
пароли Redis, лимиты памяти и production rate limits. Изменено только то, без
чего стенд нельзя поднять локально и измерить:

- образы собираются из checkout с тегом прогона;
- синтетические секреты лежат во временном каталоге с правами 0700: JWT-ключи,
  сертификаты RPC, сертификат Gateway от одноразового CA и случайные пароли;
- Gateway опубликован на случайном порту loopback вместо 443, а его healthcheck
  доверяет одноразовому CA;
- Auth, Chat и Gateway отдают метрики во внутреннюю сеть `load-metrics`.

Приглашения оркестратор записывает в БД Auth напрямую. Снимки ресурсов он
берёт на границах фаз только на чтение: у Docker Engine API — CPU и пиковую
память контейнеров (опрос раз в секунду), у PostgreSQL Auth и Chat —
`pg_stat_database`, у Redis — `INFO`.

## Профиль

Профиль и пороги лежат в [internal/chatload/profile.json](../../internal/chatload/profile.json).
Последовательность операций, тексты и `client_message_id` задаются seed 181,
поэтому каждый запуск отправляет одни и те же запросы по тому же расписанию.

| Параметр | Значение |
|---|---|
| Пользователи | 120; у каждого свой HTTP-клиент и одно соединение WebSocket |
| Комнаты | 60 личных диалогов и 12 приватных каналов по 10 участников: каждый пользователь в одном диалоге и одном канале |
| Запись | 40 новых сообщений/с (в среднем одно сообщение в 3 с от каждого), текст 32–512 байт; 2 % отправок повторяются с тем же `client_message_id` |
| Чтение | 20 запросов/с: половина — `GET /rooms`, половина — страница истории из 50 сообщений |
| Рассылка | Событие получают все участники комнаты, в среднем 6: около 240 событий WebSocket в секунду |
| Расписание | Открытая модель нагрузки: время каждой операции случайно и равномерно распределено внутри фазы, число операций фиксировано (`скорость × длительность`); ответы сервера расписание не замедляют |
| Фазы | Прогрев 20 с, 3 серии по 60 с, переподключение 40 с, ступени 60/80/100/120/140 сообщений/с по 30 с |
| Токены | Срок access token как на VPS (15 мин); клиент обновляет его за 90 с до истечения и заново аутентифицирует WebSocket |

После каждой фазы, уже вне измерения, все клиенты выполняют догрузку по
[realtime.md](../chat/realtime.md#reconnect-and-catch-up). Затем генератор
читает полную историю каждой комнаты и сверяет:

- в истории нет пропущенных `sequence`;
- ни один `client_message_id` не сохранён дважды, повтор с тем же
  `client_message_id` возвращает то же сообщение;
- каждое подтверждённое сообщение есть в истории;
- у каждого участника есть вся история комнаты без чужих сообщений на тех же
  номерах.

В фазе переподключения 20 клиентов закрывают WebSocket через 5 с после начала,
10 с остаются без соединения, пока остальные пишут, в том числе в их комнаты.
Затем они подключаются в течение 5 с, как клиенты с backoff и jitter, и сразу
догружают пропущенное.

## Пороги

Пороги относятся к каждой серии и к фазе переподключения. Ступени нагрузки
только измеряются и показывают, где пороги перестают выполняться.

| Метрика | Порог | Обоснование |
|---|---|---|
| Отправка `POST /messages`, p95 / p99 | 100 / 250 мс | Отправка ощущается мгновенной |
| Чтение, p95 / p99 | 100 / 250 мс | Открытие комнаты и списка без заметной задержки |
| Доставка от начала отправки до события у получателя, p95 / p99 | 150 / 300 мс | Собеседник видит сообщение практически сразу |
| Ошибки запросов | ≤ 0,1 % | Включая 429 и таймауты |
| Пропускная способность | ≥ 98 % цели | Подтверждённые новые сообщения / (40 × длительность) |
| Живая доставка | ≥ 99,9 % | События, полученные подключёнными участниками; в фазе переподключения не проверяется |
| Целостность | 0 нарушений | Пропуски, дубликаты, потерянные подтверждённые сообщения, неполные истории клиентов |
| Повторные события | 0 | Одно и то же событие дважды по WebSocket |
| События, сброшенные Chat, ошибки публикации | 0 | `vault_events_dropped_total`, `vault_events_publish_failures_total` |
| Неожиданные закрытия WebSocket | 0 | Например, 4002 у медленного клиента |
| Память контейнера | ≤ 90 % лимита | Пик за фазу; перезапусков и OOM нет |
| Переподключение с догрузкой | ≤ 3 с | От начала подключения до конца догрузки |
| Повторяемость серий | CV пропускной способности ≤ 5 %, max/min p95 ≤ 1,5 | Отдельно для отправки, чтения и доставки |
| Метрики сервисов | читаются весь прогон | Иначе нули выглядели бы как успех |

Профиль отклоняется, если превышает production-лимит пользователя (120
запросов в минуту; генератору разрешено не больше 75 %). Поэтому ступени
упираются в стенд, а не в лимит пользователя.

Эталонный отчёт — [chat-2026-11-24.json](chat-2026-11-24.json). Он снят на
коммите `2bd4ac3` с чистым рабочим деревом, все пороги выполнены. Подготовка
данных заняла 76 с: регистрация и вход 30 с, комнаты 1 с, подключения 45 с.

| Фаза | Сообщений/с | Отправка p50 / p95 / p99, мс | Чтение p95 / p99, мс | Доставка p50 / p95 / p99, мс | Ошибки | CPU стенда |
|---|---|---|---|---|---|---|
| Серия 1 | 40,0 | 16,5 / 44,3 / 82,6 | 36,2 / 71,5 | 25,1 / 65,2 / 121,0 | 0 | 1,17 |
| Серия 2 | 40,0 | 14,9 / 36,4 / 61,8 | 29,1 / 51,5 | 22,8 / 52,3 / 83,5 | 0 | 1,10 |
| Серия 3 | 40,0 | 15,4 / 43,8 / 70,1 | 37,7 / 65,4 | 23,9 / 67,6 / 100,2 | 0 | 1,16 |
| Переподключение | 40,0 | 16,1 / 41,5 / 58,5 | 31,8 / 48,3 | 24,6 / 59,0 / 84,8 | 0 | 1,12 |

В каждой серии:

- подтверждено 2400 из 2400 сообщений;
- выполнено 1200 чтений;
- 36–46 повторов с тем же `client_message_id` вернули исходное сообщение;
- подключённые участники получили по WebSocket все 14,4 тыс. событий, около 240
  в секунду, без повторов;
- проверка целостности не нашла нарушений;
- очередь событий Chat не превышала 1 из 1024;
- нагрузка на базы и Redis: PostgreSQL Chat — 60 транзакций/с и 38 вставок/с,
  PostgreSQL Auth — 470 транзакций/с, Redis — 910 команд/с;
- пиковая память — не больше 28 % лимита, перезапусков нет.

В фазе переподключения все 20 клиентов вернулись. Подключение вместе с
догрузкой заняло p50 47 мс и не больше 112 мс, клиенты догрузили 492
пропущенных сообщения. После догрузки у каждого участника полная история.

Отношение max/min p95 между сериями прогона: отправка 1,22, чтение 1,29,
доставка 1,29 при пороге 1,5. Пропускная способность во всех сериях — ровно
40,0 сообщения/с. Три прогона одного коммита на одной машине:

| Прогон | Отправка p95 по сериям, мс | Доставка p95, мс | Чтение p95, мс | Пороги выполняются до, сообщений/с |
|---|---|---|---|---|
| 1 (рабочее дерево с черновиком этого документа) | 34,0–35,1 | 48,4–51,9 | 27,6–30,3 | 80 |
| 2 (то же) | 31,7–43,3 | 47,2–62,9 | 25,5–36,4 | 80 |
| 3, эталонный | 36,4–44,3 | 52,3–67,6 | 29,1–37,7 | 60 |

На целевой нагрузке результаты повторяются с разбросом p95 около 10 мс. Порог
на ступенях повторяется хуже. На 80 сообщениях/с p95 отправки было 60–101 мс
при пороге 100. Значит, 80 сообщений/с — граница запаса, а не гарантированный
запас: на Docker Desktop на результат влияет остальная нагрузка машины.

## Узкое место

Узкое место — Auth и его PostgreSQL. На целевой нагрузке Auth занимает 0,44
CPU из 1,1, потраченных всем стендом. Вместе со своей базой (0,09) это около
половины CPU стенда, хотя Auth не участвует в самой переписке. Chat вместе с
базой занимает 0,23 CPU, Gateway — 0,25, Redis — 0,04.

Причина — число проверок токена. Каждая проверка `ValidateToken` — одна
транзакция в PostgreSQL Auth: в серии около 470 транзакций/с против 60 у
Chat. Вызовов в секунду получается D + C + 2R:

- D — доставленные события: Gateway проверяет сессию перед каждым событием
  WebSocket ([realtime.go](../../internal/gateway/handler/realtime.go), `relay`);
- C — открытые соединения: раз в секунду каждое соединение проверяется ещё
  раз, даже без событий;
- R — REST-запросы: каждый проверяет Gateway, а затем Chat
  ([grpc.go](../../internal/chat/handler/grpc.go)).

На 40 сообщениях/с это 239 + 120 + 2 × 61 = 481 вызов/с, измерено 481. На
100 сообщениях/с — 599 + 120 + 2 × 122 = 963, измерено 963. Нагрузка на Auth
растёт с размером комнат, а не с числом сообщений: сообщение в канал из 10
участников стоит 10 проверок.

По ступеням эталонного прогона стенд упирается в два CPU:

| Нагрузка, сообщений/с | 40 | 60 | 80 | 100 | 120 | 140 |
|---|---|---|---|---|---|---|
| CPU стенда из 2 | 1,10–1,17 | 1,40 | 1,58 | 1,73 | 1,82 | 1,77 |
| CPU Auth | 0,45–0,47 | 0,56 | 0,64 | 0,70 | 0,74 | 0,72 |
| Вызовов Auth/с | 481 | 653 | 811 | 960 | 1114 | 1233 |
| Отправка p95, мс | 36–44 | 60 | 101 | 166 | 279 | 581 |
| Доставка p95, мс | 52–68 | 85 | 145 | 258 | 502 | 7163 |

Все пороги выполняются до 60–80 сообщений/с, то есть при 1,5–2-кратной
целевой нагрузке. На 100 сообщениях/с стенд занимает 1,7 CPU из 2, и p95
отправки и доставки выходят за пороги во всех прогонах. На 120–140
сообщениях/с CPU насыщен:
- генератор держит до 100 запросов одновременно;
- Gateway начинает отвечать 429 (см. находки);
- задержка доставки растёт до секунд;
- медленные клиенты отключаются с кодом 4002 и потом догружают пропущенное.

Очередь событий Chat не превышала 2 из 1024. Redis выполнял 0,9–2,5 тыс.
команд/с при 0,07 CPU. Попадание в кэш PostgreSQL — 100 %. Пиковая память не
превышала трети лимита ни у одного контейнера. Ни Chat, ни Redis, ни базы не
ограничивают пропускную способность раньше Auth.

Снизить нагрузку можно двумя способами:

- проверять сессию не перед каждым событием, а не чаще раза в секунду на
  соединение, полагаясь на подсказки Redis об отзыве;
- не проверять токен повторно в Chat, если вызов пришёл от Gateway по mTLS.

Первый способ на целевой нагрузке убирает около половины вызовов Auth. Оба
меняют решение 8 из [требований](../requirements.md) (проверка сессии при
каждом обращении), поэтому требуют отдельного ADR. В этой задаче они не
сделаны.

## Находки

1. **Auth проверяет токен на каждое событие и каждый запрос** — см. «Узкое
   место».
2. **WebSocket и лимит на адрес.** Подключение WebSocket тратит токен общего
   бакета адреса (30 подряд, затем 2 в секунду), и этот токен не возвращается.
   - 120 клиентов с одного адреса подключались 45 с, апгрейд отклонялся 178
     раз. Пользователи за одним NAT после перезапуска Gateway будут так же
     подключаться до минуты.
   - Пока лимит исчерпан, соседи по адресу получают 429 и на REST. В пробном
     прогоне 20 клиентов, переподключившихся одновременно, вызвали три 429 у
     других пользователей. В профиле переподключения поэтому разнесены на 5 с.
   - При перегрузке REST-запрос держит токен адреса, пока Auth проверяет его
     access token. Больше 30 медленных запросов сразу исчерпывают бакет: от 59
     до 275 ответов 429 на ступени 140 сообщений/с в разных прогонах.
3. **Auth хеширует не больше двух паролей одновременно** и отвечает 503
   «password capacity reached» остальным. Регистрация и вход 120 пользователей
   заняли 26–30 с, генератор повторяет такие запросы. Массовый вход после отзыва
   всех сессий будет растянут так же.
4. **Целостность сохраняется даже при перегрузке.** Во всех фазах всех прогонов,
   включая 140 сообщений/с, проверка не нашла ни одного нарушения: пропусков в
   истории, повторно сохранённых сообщений, потерянных подтверждённых сообщений
   или неполной истории у клиента. Повторов события по WebSocket тоже не было.
   - Повтор с тем же `client_message_id` (2 % отправок) всегда возвращал
     исходное сообщение.
   - Клиенты, отключённые с кодом 4002, догрузили пропущенное через catch-up.

## Что не проверяется

- Это не измерение VPS: стенд и генератор работают на одной машине под Docker
  Desktop, разделены только по CPU. Сети между клиентом и сервером нет, поэтому
  задержки ниже, чем у реальных клиентов.
- Все клиенты приходят с одного адреса, как пользователи за одним NAT.
  Лимиты на адрес действуют на всех сразу (см. находки).
- Не нагружаются вложения (Media, S3), push, звонки и раздача статики
  веб-клиента. Браузер не запускается: генератор повторяет протокол веб-клиента,
  а не его отрисовку.
- Одна реплика Gateway и каждого сервиса, как на VPS.
