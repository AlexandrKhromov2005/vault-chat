# Демонстрация Vault Chat

Сценарий для ручного показа веб-клиента на стенде из Docker Compose. Он
покрывает пункты плана из [требований](requirements.md):

- переписку и обмен файлом;
- запрет доступа третьему пользователю;
- восстановление соединения: переподключение, обновление токена, догрузку
  сообщений и пересинхронизацию комнат.

Основные шаги этих сценариев повторяют автоматические проверки в конце
документа.

## Подготовка стенда

Нужны Docker с Compose v2, OpenSSL и браузер. Go и Node.js для показа не нужны.

```sh
git clone https://github.com/AlexandrKhromov2005/vault-chat.git
cd vault-chat
sh scripts/gen-jwt-keys.sh
AUTH_JWT_ACCESS_TTL=2m docker compose -f deployments/docker-compose.yml up -d --build --wait
curl --fail http://localhost:8080/ready
```

`AUTH_JWT_ACCESS_TTL=2m` сокращает жизнь access token с 15 до 2 минут, чтобы
обновление токена было видно за время показа (сценарий 5). Первая сборка
занимает несколько минут: локальное S3 собирается из исходного кода.

Откройте `http://localhost:8080/` в трёх вкладках одного браузера. Вход
хранится в `sessionStorage` вкладки, поэтому в каждой вкладке свой пользователь.
Открывайте вкладки заново, а не дублированием: дубликат копирует refresh token,
и Auth примет его повторное использование за кражу.

| Вкладка | Email | Имя | Пароль |
|---|---|---|---|
| 1 | `alice@example.com` | `alice` | `Password123` |
| 2 | `bob@example.com` | `bob` | `Password123` |
| 3 | `eve@example.com` | `eve` | `Password123` |

Зарегистрируйте пользователей на вкладке «Регистрация». Справа вверху должно
появиться имя пользователя и индикатор «в сети».

## Сценарий 1. Переписка и обмен файлом

1. **alice**: введите в поиск `bo` и выберите `bob`. Откроется личный диалог.
2. **alice**: напишите сообщение и нажмите Enter.
   **bob**: диалог появляется в списке с отметкой непрочитанного, без
   перезагрузки страницы.
3. **bob**: откройте диалог и ответьте. Ответ сразу появляется у alice.
4. **alice**: нажмите «Файл» и выберите PNG, JPEG, PDF или текстовый файл до
   10 МиБ. Над полем ввода появится вложение. Отправьте сообщение, текст можно
   не писать.
5. **bob**: нажмите на вложение в сообщении. Файл сохраняется под исходным
   именем и не открывается в странице.

## Сценарий 2. Третий пользователь не получает доступа

1. **eve**: список комнат пуст. Диалога alice и bob в нём нет.
2. **eve**: найдите `alice` и откройте диалог. Создаётся отдельный диалог
   eve–alice; сообщения и файлы alice и bob в нём не видны.
3. Прямой запрос к чужой комнате и чужому файлу тоже отклоняется. ID комнаты
   и файла видны во вкладке alice в инструментах разработчика (Network:
   запросы `/api/v1/rooms/<room_id>/messages` и `/api/v1/files/<file_id>`):

   ```sh
   TOKEN=$(curl -s http://localhost:8080/api/v1/auth/login \
     -H 'Content-Type: application/json' \
     -d '{"email":"eve@example.com","password":"Password123"}' |
     sed -E 's/.*"access_token":"([^"]+)".*/\1/')
   curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/rooms/<room_id>/messages
   curl -i -H "Authorization: Bearer $TOKEN" http://localhost:8080/api/v1/files/<file_id>/content
   ```

   Оба запроса возвращают `404`. Чужая комната неотличима от
   несуществующей, поэтому ответ не раскрывает даже факт её существования.
4. **alice**: создайте канал «Проект», откройте «Участники», добавьте `bob`
   и отправьте в канал файл. **bob** видит канал и может скачать файл.
5. **alice**: удалите `bob` из канала. **bob**: канал сразу исчезает из списка.
   Ссылка на файл канала для него больше не работает: Media проверяет текущее
   членство при каждом запросе.

## Сценарий 3. Переподключение и догрузка сообщений

События в реальном времени доставляются без гарантии: при обрыве они
теряются, а клиент восстанавливает пропущенное по номерам сообщений
(`docs/chat/realtime.md`). Чтобы это показать, остановите Redis. Через него
идут события, а REST продолжает работать.

1. **bob**: откройте диалог с alice. Откройте инструменты разработчика
   (F12), вкладку Network, и нажмите очистку списка запросов.
2. Остановите Redis:

   ```sh
   docker compose -f deployments/docker-compose.yml stop redis
   ```

   Уже открытое соединение может ещё долго (в проверке — больше двух
   минут) показывать «в сети»: Gateway замечает потерю Redis не сразу. Но
   события по нему не приходят, потому что Chat не может их опубликовать.
   Новое подключение, например после перезагрузки вкладки, не получает
   `ready`: подписка на события без Redis не проходит, поэтому индикатор
   показывает «переподключение…» до запуска Redis. Когда Gateway обнаруживает
   потерю, он так же закрывает и открытые соединения.
3. **alice**: отправьте два сообщения. Они сохраняются, потому что REST
   работает без Redis, и видны у alice из ответа на отправку. **bob**: в
   диалоге их нет.
4. Запустите Redis:

   ```sh
   docker compose -f deployments/docker-compose.yml start redis
   ```

   **bob**: индикатор переходит в «в сети», и оба сообщения появляются в
   диалоге по порядку. В Network видно, как они пришли: после подключения к
   `/api/v1/ws` клиент делает запрос
   `GET /api/v1/rooms/<room_id>/messages?limit=100&after=<номер>`, то есть
   догружает пропущенное по REST. Событий об этих сообщениях в WebSocket нет:
   они потеряны вместе с Redis, и восстанавливает их именно догрузка.

Отличить живую доставку от догрузки можно так: при работающем Redis новое
сообщение приходит кадром `message.created` в WebSocket (Network → запрос
`ws` → вкладка Messages), без отдельного запроса `messages?...&after=`.

Обрыв самого Gateway показывается так же:

```sh
docker compose -f deployments/docker-compose.yml restart gateway
```

Соединения закрываются кодом 1001, клиент переподключается с нарастающей
задержкой и после `ready` догружает сообщения.

## Сценарий 4. Пересинхронизация комнат

Изменения состава комнат, сделанные во время обрыва, тоже не повторяются.
Клиент узнаёт о них, перечитывая список комнат после каждого переподключения.

1. Остановите Redis, как в сценарии 3.
2. **alice**: создайте канал «Новости» и добавьте в него `bob`; удалите `bob`
   из канала «Проект», если вы снова его туда добавили.
3. Запустите Redis. **bob**: после переподключения «Новости» появляются
   в списке с отметкой непрочитанного, а «Проект» исчезает.

## Сценарий 5. Обновление токена

Стенд запущен с `AUTH_JWT_ACCESS_TTL=2m`: access token живёт 2 минуты.
Без обновления через 2 минуты Gateway закрыл бы WebSocket кодом 4001, а
REST-запросы получали бы `401`. Значит, если через 3–4 минуты всё работает
без переподключений, токен обновляется. Как это увидеть:

1. **bob**: войдите заново или перезагрузите страницу, затем откройте
   инструменты разработчика (F12) и вкладку Network.
2. Введите в поле фильтра `refresh`. Примерно каждые 30 секунд, то есть за
   90 секунд до истечения двухминутного токена, появляется
   `POST /api/v1/auth/refresh`. Нажмите на него: на вкладке ответа
   (Response или Preview) `access_expires_at` на 2 минуты позже текущего
   времени, а `access_token` каждый раз новый.
3. Очистите фильтр и выберите тип WS (в Chrome и Edge кнопка «WS», в
   Firefox — «WS» в списке типов). Нажмите на запрос `ws`, затем на вкладку
   Messages (в Firefox — Response). Каждые 30 секунд клиент отправляет кадр
   `{"type":"auth","token":"…"}` с новым токеном, а Gateway отвечает
   `{"type":"ready",…,"expires_at":"…"}`, и `expires_at` сдвигается вперёд.
4. Подождите 3–4 минуты и отправьте сообщение из вкладки bob. Индикатор
   всё это время показывал «в сети», новых подключений к `ws` в списке нет
   (оно одно, с начала проверки), отправка работает, и выхода на экран входа
   не было.

Как устроено обновление:
- пока открыто WebSocket-соединение, клиент за 90 секунд до истечения
  получает новый access token и отправляет его в соединение кадром `auth`.
  Кадры `auth` уходят не чаще раза в 10 секунд, иначе Gateway закрывает
  соединение с кодом 1008;
- REST-запросы сами обновляют токен, если до истечения меньше минуты;
- если токен всё же отклонён (код 4001), клиент обновляет его и сразу
  переподключается;
- отклонённый refresh token завершает вход.

## Автоматическая проверка

Те же сценарии проверяются против запущенного стека:

```sh
VAULT_CHAT_WEB_GATEWAY_URL=http://127.0.0.1:8080 node --test "web/test/*.test.mjs"
VAULT_CHAT_COMPOSE_GATEWAY_URL=http://127.0.0.1:8080 go test -tags compose -count=1 ./tests/compose/...
```

Первая команда (Node.js 22+) проходит клиентскими модулями:
- регистрация, вход, обновление токена и выход;
- личный диалог и каналы;
- обмен файлом и запрет доступа постороннему и удалённому участнику;
- доставка событий, обрыв соединения и догрузка пропущенного.

Вторая команда (Go) проверяет доставку и вложения через REST и WebSocket.

## Остановка

```sh
docker compose -f deployments/docker-compose.yml down -v
```

`-v` удаляет данные стенда, в том числе созданных пользователей.
