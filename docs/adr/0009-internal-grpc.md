# ADR 0009: gRPC для внутренних вызовов

Статус: принято. Дата: 2026-11-24. Решение действует с первых версий;
этот ADR записывает его задним числом.

## Контекст

Сервисы ([ADR 0008](0008-service-decomposition.md)) вызывают друг друга
синхронно: Gateway переводит каждый клиентский запрос в вызов владельца
данных, Chat и Media проверяют токен в Auth, Media спрашивает Chat о членстве,
Chat спрашивает Media о вложениях. Загрузка и скачивание файлов идут потоком
до 10 МиБ.

От внутреннего протокола нужны: строгий контракт, общий для сервера и
клиента; проверка идентичности вызывающего сервиса и права на метод;
ограниченные сообщения и время; потоковая передача.

## Решение

- **gRPC поверх HTTP/2, библиотека `google.golang.org/grpc`.** Контракты —
  Protobuf в `api/proto/<service>/v1`, код генерирует `buf`
  (`api/gen`). Клиенты публичного API работают с REST/JSON Gateway
  ([OpenAPI](../api/gateway.yaml)); gRPC наружу не публикуется.
- **Идентичность и ACL.** На VPS каждый вызов идёт по mTLS: клиент проверяет
  точную идентичность сервера, сервер — CA и URI SAN клиента, а
  interceptors пропускают только методы из матрицы, по умолчанию отказ
  ([ADR 0001](0001-internal-mtls.md), [mTLS](../mtls.md)). Проверка
  действует и для потоков. Reflection включается только без mTLS, в локальной
  разработке.
- **Пользователь передаётся отдельно от сервиса.** Gateway кладёт токен
  пользователя в metadata `authorization`, и владелец данных сам проверяет
  его в Auth. Сертификат сервиса не заменяет права пользователя: без
  действующего токена Gateway не может действовать от имени пользователя
  ([ADR 0011](0011-authentication-and-sessions.md)).
- **Ограничения.** Chat принимает сообщения до 1 МиБ, Media — кадры до
  128 КиБ (файл идёт потоком). Deadline задаёт вызывающий: Gateway — 10 с на
  JSON-запрос (`GATEWAY_REQUEST_TIMEOUT`), пять минут и 30 с без прогресса на
  передачу файла; Chat дополнительно ограничивает каждый вызов
  `CHAT_REQUEST_TIMEOUT`. Автоматических повторов RPC нет: повтор решает
  клиент, а отправка сообщения идемпотентна по `client_message_id`.
- **Ошибки.** Сервисы отвечают кодами gRPC, Gateway отображает их в HTTP и
  не пересылает текст внутренних ошибок.
- **Версионирование.** Пакеты имеют суффикс версии (`auth.v1`, `chat.v1`),
  `buf lint` с правилами `STANDARD` это требует. Внутри `v1` допустимы только
  совместимые изменения: новые поля и методы, без смены номеров и типов полей.
  Несовместимое изменение — новый пакет `v2`, который обслуживается рядом со
  старым, пока все вызывающие не перейдут.

## Альтернативы

- **Внутренний REST/JSON.** Не нужен отдельный кодогенератор, проще отладка
  через curl. Отклонён: контракт пришлось бы поддерживать вручную в двух
  местах, нет общей модели потоков и deadline, а ACL по методу пришлось бы
  строить на путях URL.
- **Connect-RPC.** Совместим с gRPC и даёт HTTP/1.1 и JSON для браузера.
  Отклонён: браузер с внутренними сервисами не говорит, а у `grpc-go` более
  зрелые interceptors, credentials для mTLS и health-протокол, которые нужны
  каждому сервису.
- **Только брокер сообщений.** Асинхронность не подходит для запросов,
  которым нужен ответ сразу (проверка токена, членство). Брокер используется
  там, где ответ не нужен: события чата и push
  ([ADR 0003](0003-push-signals-jetstream.md)).

## Последствия

- Отладка требует `grpcurl` и, на VPS, клиентского сертификата; reflection
  там выключен.
- Совместимость `v1` проверяют только ревью и `buf lint`. Конфигурация
  `buf breaking` (`FILE`) лежит в `api/proto/buf.yaml`, но в `xmake ci`
  сравнение с `main` не подключено. Пока все сервисы выпускаются одним тегом,
  несовместимое изменение ломает сборку и тесты, а не работающий стенд;
  автоматическая проверка нужна до раздельного выпуска сервисов.
- Синхронная цепочка переносит отказ: без Auth не работает ни один
  защищённый запрос. Это сознательная плата за проверку сессии при каждом
  обращении (ADR 0011).
- HTTP/2 и TLS добавляют процессорную стоимость на каждый вызов; при
  нагрузке (#181) она меньше, чем стоимость транзакций проверки токена.

## Проверки

- `TestMutualTLSOverTCP` (`internal/shared/rpctls`): реальные TLS-handshake;
  чужой CA, неверная идентичность сервера, неизвестный подписанный сервис и
  истёкший сертификат отклоняются.
- `TestRPCPermissions` и `TestServiceMethodMatrixAndStreams`: матрица методов
  для unary и stream, отказ reflection и методов вне матрицы.
- `TestFailClosedConfiguration`: неполная настройка mTLS останавливает
  процесс, а не включает plaintext.
- `TestEveryRPC_RejectsMissingIdentity` (`internal/chat/handler`): вызов Chat
  без токена пользователя отклоняется даже от разрешённого сервиса.
- `TestRoomFailures_AreClassifiedWithoutLeakingInternals` и
  `TestChatREST_UsesSafeBackendErrorMapping`: внутренние ошибки не доходят
  до клиента.
- `xmake proto` (`buf lint`) — суффикс версии пакета и стиль контрактов.

```sh
go test -count=1 -run 'TestMutualTLSOverTCP|TestRPCPermissions|TestServiceMethodMatrixAndStreams' ./internal/shared/rpctls/
buf lint api/proto
```
