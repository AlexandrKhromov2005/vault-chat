# ADR 0007: доступ мониторинга к сервисам после разделения сетей

Статус: принято. Дата: 2026-11-06. Закрывает конфигурационную часть #120.

## Контекст

После разделения сетей (#102) сервисы VPS подключены только к `internal`-сетям,
кроме Gateway (`edge`). Мониторинг (`docker-compose.monitoring.yml`) рассчитан на
другое, и в #120 это подтверждено по `main`:

- Prometheus, Alertmanager, Grafana и node exporter работают в сети хоста и
  читают `127.0.0.1`. Overlay `monitoring/app.yml` публикует metrics-порты
  9101–9104 на loopback, но Docker не публикует порты контейнера, у которого
  есть только `internal`-сети. Работает только порт Gateway.
- Blackbox подключён только к `rpc`. Его `127.0.0.1:9115` поэтому тоже не
  опубликован, а Redis, PostgreSQL и MinIO из `rpc` не разрешаются.
- Последствия для алертов: `ServiceMetricsUnavailable` зажжётся для Auth, Chat,
  Media и blackbox через 2 минуты. Но неудачный scrape проб не создаёт
  `probe_success == 0`, поэтому `DependencyUnavailable` и `CertificateExpiring`
  слепы, а `up` у probe-jobs в селектор не входит.

Ограничение из ревью #120: не делать существующие `internal`-сети обычными и не
давать backend-сервисам лишний egress.

**Проверенный факт** (Docker 29.4.0, VM разработки, 2026-11-06): у хоста есть
адрес на мосту `internal`-сети, и процесс хоста подключается к контейнеру в ней
по IP. Сеть при этом остаётся без выхода наружу. Решение опирается на это
поведение, поэтому его версия на VPS — первый пункт приёмки.

## Решение

**Граница доверия — хост.** Читать метрики и проверять зависимости могут только
процессы хоста (мониторинг в `network_mode: host`, root); контейнеры получают не
больше связности, чем сейчас.

1. **Отдельная сеть метрик на сервис.** `metrics-auth`, `metrics-chat`,
   `metrics-media`, `metrics-gateway`: `internal: true`, фиксированная подсеть
   `/29`, в каждой ровно один контейнер с фиксированным адресом. Listener метрик
   слушает только этот адрес (`AUTH_METRICS_ADDR=<ip>:9100`), а не `:9100`.
   Сервисы не видят метрики друг друга, и между ними не появляется новых путей.
   Публикация портов 9101–9104 из `app.yml` убирается.
2. **Prometheus читает `<ip>:9100` напрямую** из сети хоста. Адреса берутся из
   одного места (`.env.monitoring`) и в Compose, и в генераторе конфигурации.
3. **Blackbox переходит в сеть хоста** и слушает `127.0.0.1:9115`. Хранилищам
   данных и MinIO в их `internal`-сетях задаются фиксированные адреса, и
   blackbox проверяет TCP и `/minio/health/ready` по ним. Доступа по паролю у
   проб нет; Redis и PostgreSQL принимают только TCP-подключение.
4. **Алерты не слепнут.** `ServiceMetricsUnavailable` включает probe-jobs
   (`gateway-ready`, `storage-ready`, `data-tcp`). Добавляется правило на
   отсутствие серии: нет `probe_success` для ожидаемого target 5 минут — алерт.

Подсети выбираются из `172.31.240.0/20` и проверяются на пересечение с
существующими сетями до `up`; при пересечении развёртывание останавливается.

## Альтернативы

| Вариант | Почему нет |
|---|---|
| Сделать `rpc` или сети данных обычными | Даёт backend-сервисам выход в интернет и снимает изоляцию #102 |
| Одна общая сеть `metrics` для четырёх сервисов | Сервисы на ней видят listeners друг друга; отдельные сети стоят столько же |
| Prometheus в bridge-сети с сервисами | Ему всё равно нужен host loopback для node exporter и Alertmanager; появляется контейнер, связанный со всеми сервисами |
| Blackbox во всех сетях данных | Одна точка, из которой достижимы все базы |
| Каждый сервис сам экспортирует здоровье своих зависимостей | Хорошее дополнение, но требует кода в каждом сервисе и не покрывает MinIO и сертификат; можно позже |

## Поведение при сбоях

| Сбой | Поведение |
|---|---|
| Сервис упал или его listener не отвечает | `up == 0`, `ServiceMetricsUnavailable` через 2 мин |
| Blackbox не запущен | `up{job=~"gateway-ready\|storage-ready\|data-tcp"} == 0`, тот же алерт |
| Redis, PostgreSQL или MinIO недоступны | `probe_success == 0`, `DependencyUnavailable` через 2 мин |
| Нет серии пробы (target пропал из конфигурации) | Алерт на отсутствие серии через 5 мин |
| Docker на VPS не даёт хосту доступа к `internal`-сети | Приёмка 1 падает до выката; решение пересматривается |
| Пересечение подсетей | Проверка до `up` останавливает развёртывание |

## Приёмочные тесты (одноразовый локальный Docker)

1. Версия Docker совпадает с VPS, и хост достаёт контейнер в `internal`-сети по IP.
2. `curl` с хоста на `<ip>:9100` каждого из четырёх сервисов и на
   `127.0.0.1:9115` blackbox отвечает; `up == 1` у всех targets Prometheus.
3. Пробы Gateway, MinIO, Redis и трёх PostgreSQL успешны.
4. Внедрение сбоев: остановленный Chat, остановленные Redis и PostgreSQL,
   остановленный blackbox — соответствующий алерт переходит в `firing`.
5. Изоляция: ни один metrics- или probe-порт не слушает не-loopback адрес хоста;
   из контейнера Chat недоступны `<ip>:9100` Auth и адреса хранилищ других
   сервисов; из `internal`-сетей нет выхода наружу.
6. Статические проверки (`check-monitoring.sh`, `check-deployment.sh`): каждая
   сеть метрик `internal` и содержит один контейнер, listener привязан к адресу,
   подсети не пересекаются.

Сценарии и их запуск коммитятся вместе с исправлением; заявления в
`docs/monitoring.md` обновляются только после их прохождения.
