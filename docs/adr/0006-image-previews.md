# ADR 0006: превью изображений — контракт, изоляция и gates для Zig

Статус: предложено. Дата: 2026-11-03, переработано 2026-11-05 по ревью #122.
Этап Z1 из [ARCHITECTURE §12.2](../../ARCHITECTURE.md#122-zig-isolated-media-processing);
владелец направления — Tagir. Замер базовой линии на Go — следующие PR этого
этапа; прототип на Zig — этап Z2.

## Контекст

Media принимает PNG и JPEG до 10 МиБ и не больше 40 миллионов пикселей по
заголовку, хранит оригинал в приватном S3 и отдаёт его только участникам
комнаты ([files](../media/files.md)). Превью нет: веб-клиент показывает вложение
кнопкой скачивания.

Ограничения, которые определяют дизайн:

- **Память.** Декодирование стандартными декодерами берёт от 1 до 24 байт на
  пиксель в зависимости от кодировки (16 бит, interlace, progressive, CMYK),
  а у контейнера Media на VPS `mem_limit` 256 МиБ. Декодирование в процессе
  Media ставит под угрозу загрузку и скачивание всех файлов. Поэтому превью
  делается в отдельном процессе **независимо от языка**.
- **Недоверенный ввод.** Файл прошёл проверку сигнатуры и заголовка, но не
  санитизацию; декодер разбирает данные злоумышленника.

**Язык.** Zig выбран владельцем архитектуры для изолированного декодера превью
(ревью #122, 2026-11-04); Auth, Chat, Media и Gateway остаются на Go. Это
архитектурное решение, а не результат замера. Реализация на Go — эталон для
корректности и измерений. Выигрыш в 2 раза — измеряемая гипотеза, а не условие
отказа; недостижение требует анализа и оптимизации, а не возврата к Go. Выкат
блокируют только gates ниже; смена языка — отдельное явное решение владельца.

## Контракт превью

| Параметр | Значение |
|---|---|
| Вход | Файл с типом `image/png` или `image/jpeg`, определённым Media по содержимому |
| Размер | Длинная сторона не больше 320 px, пропорции сохраняются, меньшие изображения не увеличиваются |
| Уменьшение | Усреднение по площади: исходный пиксель входит в пиксели превью пропорционально перекрытию |
| Ориентация | EXIF Orientation 1–8 у JPEG применяется к превью |
| Выход | JPEG baseline, качество 80, 4:2:0, кодирует Media; прозрачность накладывается на белый |
| Метаданные | Отсутствуют по построению: JPEG создаёт кодировщик Media из пикселей |
| Цвет | Отсчёты трактуются как sRGB; ICC-профиль не применяется (см. ниже) |
| Детерминизм | Одинаковый вход и версия декодера дают одинаковые пиксели |

**Цвет.** Игнорирование ICC не преобразует wide-gamut вход в sRGB, а
отбрасывает сведения, нужные для преобразования. Фото в Display P3 или Adobe RGB
получат сдвиг цвета (менее насыщенные), CMYK-JPEG — грубое преобразование без
профиля, 16-битные отсчёты усекаются до 8 бит. Это принято для первого этапа и
одинаково для Go и Zig; преобразование по ICC — отдельное решение.

## Решение

### Топология

Два контейнера `media-preview-1` и `media-preview-2`, каждый выполняет одну
задачу за раз. В контейнере работает супервизор на Go: gRPC-сервер по mTLS с
идентичностью сервиса ([ADR 0001](0001-internal-mtls.md)). На каждую задачу он
запускает свежий процесс-декодер (эталон на Go, кандидат на Zig), пишет ему в
stdin байты оригинала и читает из stdout ширину, высоту и пиксели RGB.

- Падение или OOM декодера убивает только его: супервизор отвечает ошибкой
  задачи. Падение супервизора перезапускает один контейнер; второй работает.
- Динамических контейнеров нет; сокет Docker никуда не монтируется.
- Лимиты: `mem_limit` 192 МиБ без swap, 1 CPU, `pids_limit` 16 на контейнер;
  декодеру — `RLIMIT_CPU` 2 с и дедлайн 5 с от супервизора.

### Поток

1. Media публикует файл (`pending → published`, [files](../media/files.md)) и в той
   же транзакции добавляет задачу `(file_id, preset "p320", decoder_version)`.
   Сверщик раз в 5 минут добавляет задачи для опубликованных изображений без
   задачи (не больше 100 за проход): так файл не теряет превью при сбое и при
   выходе новой версии декодера.
2. Планировщик захватывает задачу (ниже), записывает ключ будущего объекта и
   отправляет байты оригинала свободному контейнеру.
3. Media проверяет ответ: `1 ≤ w, h ≤ 320`, размеры равны `fit` исходных
   (с перестановкой для ориентаций 5–8), длина ровно `3·w·h`. Затем кодирует
   JPEG сам, пишет объект и переключает указатель.
4. `GET /api/v1/files/{file_id}/preview` читает указатель и отдаёт объект с той же
   проверкой членства через Chat, что и оригинал, и теми же заголовками
   (`private, no-store`, `nosniff`). Пока указателя нет, ответ `404`, и клиент
   показывает заглушку.

### Объекты и версии

Ключ объекта неизменяем и уникален для попытки:
`preview/<file_id>/p320/<render_id>`, `render_id` — случайный UUID. Перед записью
в S3 Media добавляет строку `preview_objects(key, file_id, state = uploading)`.
Видимую версию задаёт указатель `file_previews(file_id, preset) → key,
decoder_version`; он меняется условным обновлением в одной транзакции с
переводом задачи в `ready`, только если версия не ниже текущей.

Поэтому новая версия никогда не перезаписывает байты старой: пока задача v2 в
`pending`, `failed` или упала между S3 и БД, отдаётся v1. Сборщик удаляет
объекты в `uploading` старше часа и заменённые версии через час после
переключения указателя.

### Жизненный цикл задачи

`preview_jobs(file_id, preset, decoder_version)` — первичный ключ; поля
`state` (`pending`, `running`, `ready`, `failed`, `skipped`), `attempts`,
`next_attempt_at`, `lease_owner`, `lease_until`, `last_error`.

- **Захват** атомарный, несколько планировщиков не берут одну задачу:
  `UPDATE … SET state = running, lease_owner, lease_until = now() + 30 s,
  attempts = attempts + 1 WHERE key IN (SELECT … WHERE state = pending AND
  next_attempt_at <= now() OR state = running AND lease_until < now()
  ORDER BY next_attempt_at LIMIT <свободные слоты> FOR UPDATE SKIP LOCKED)`.
- **Завершение** условное: `WHERE lease_owner = $me AND attempts = $attempt`.
  Номер попытки — fencing token: ответ после истечения аренды не публикуется.
- **Сбой декодера** (таймаут, падение, OOM, неверный ответ) расходует попытку:
  повторы через 30 с и 5 мин, после 3 попыток — `failed`.
- **Повреждённый файл** — `failed` сразу; **больше бюджета** — `skipped`.
- **Сбой инфраструктуры** (S3, БД Media, оба контейнера недоступны до отправки)
  попытку не расходует: задача возвращается в `pending` с задержкой
  `min(10 мин, 30 с · 2^n)` и ждёт восстановления без ограничения по времени.
  Аренда, которую не удалось снять из-за отказа БД, истекает сама.

**Очередь.** Отдельного лимита очереди нет: на файл и версию декодера ровно
одна строка, поэтому очередь растёт с числом загруженных изображений, а квот
у Media пока нет. Строка — около 200 байт. Пропускная способность ограничена
двумя слотами; выход новой версии декодера ставит в очередь все изображения,
при этом старые превью продолжают отдаваться. Метрики: число `pending` и возраст
самой старой задачи, предупреждение при возрасте больше 30 минут.

### Изоляция и секреты

- Сеть `internal` только с Media; нет доступа к S3, БД, Auth, Chat, Redis и наружу.
- Файловая система только для чтения, без capabilities, `no-new-privileges`,
  непривилегированный пользователь.
- У супервизора только собственная RPC-идентичность: закрытый ключ листового
  сертификата и доверенный CA. Ключей CA, учётных данных S3, БД, JWT и
  приложения нет. Декодер запускается с пустым окружением и без секретов.
- Декодер получает байты, а не пути или URL; клиентские данные не выбирают файлы.
- gRPC: unary-запрос с явными лимитами — сервер `MaxRecvMsgSize` и клиент
  `MaxCallSendMsgSize` 10 МиБ + 64 КиБ на служебные поля, клиент
  `MaxCallRecvMsgSize` 300 КиБ + 4 КиБ. Умолчание grpc-go в 4 МиБ не используется.

## Бюджеты

| Параметр | Значение |
|---|---|
| Вход | ≤ 10 МиБ (лимит загрузки) |
| Пиксели | ≤ 24 миллиона |
| Память декодирования | ≤ 100 МиБ по оценке из заголовка (`MaxDecoded`); больше — `skipped` |
| Память процесса декодера | ≤ 140 МиБ пикового RSS |
| Контейнер | 192 МиБ, одна задача; 2 контейнера |
| Время | ≤ 2 с CPU и ≤ 5 с на задачу; превышение — отмена |
| Ответ декодера | ≤ 320 × 320 × 3 байт RGB |
| Превью | ≤ 256 КиБ JPEG |
| Повторы | 3 попытки при сбое декодера; без лимита при сбое инфраструктуры |

Оценка памяти учитывает кодировку, поэтому предел в пикселях зависит от неё:

| Кодировка | Байт на пиксель | Наибольшее превью |
|---|---|---|
| PNG до 8 бит | 4 | 24 Мп |
| PNG 16 бит или interlace | 8 | 13 Мп |
| PNG 16 бит и interlace | 16 | 6,5 Мп |
| JPEG baseline: gray, YCbCr | 1–3 | 24 Мп |
| JPEG baseline CMYK | 8 | 13 Мп |
| JPEG progressive: gray / 4:2:0 / 4:4:4 | 5 / 9 / 15 | 21 / 11,6 / 7 Мп |
| JPEG progressive CMYK | 24 | 4,4 Мп |

Изображения тяжелее — `skipped`, оригинал скачивается. Для Go-эталона оценка и
пиковый RSS на самых тяжёлых допустимых входах проверяются тестом под лимитом
cgroup; для Zig бюджеты те же.

## Поведение при сбоях

| Сбой | Поведение |
|---|---|
| Таймаут, падение или OOM декодера | Попытка не удалась; супервизор и второй контейнер работают |
| Падение супервизора | Перезапуск одного контейнера; аренда истекает, задачу берёт другой |
| Повреждённый или обрезанный файл | `failed` без повторов, заглушка |
| Неверный ответ декодера | Отбрасывается проверкой Media, попытка не удалась |
| Падение между записью в S3 и БД | Указатель не меняется, видна прежняя версия; объект удаляет сборщик |
| S3 или БД Media недоступны | Задача ждёт в `pending`, попытки не расходуются |
| Пользователь удалён из комнаты | Превью недоступно ему так же, как оригинал |

## Базовая линия, сравнение и gates

**Граница измерения.** Go и Zig сравниваются на одной границе: запуск процесса
декодера, передача байтов через stdin, декодирование, уменьшение и чтение
пикселей из stdout; время декодирования, уменьшения и передачи учитывается
отдельно. Замер `Make` внутри одного процесса (следующие PR этапа) — только
составляющая этой границы. Набор генерируется детерминированно в тестах: «фото»
(JPEG качества 90), «скриншот» (плоские цвета и резкие границы, PNG) и PNG с
прозрачностью; 1, 4, 12 и 24 мегапикселя. Для справки — `libvips` с
уменьшением при декодировании; выигрыш другой библиотеки не засчитывается языку.

**Гипотеза.** p95 времени для 12 и 24 мегапикселей ниже Go хотя бы в 2 раза
или пиковый RSS ниже хотя бы в 2 раза при том же алгоритме уменьшения.
Результат записывается в этот ADR в любом случае.

**Gates для выката декодера на Zig:**

| Gate | Условие |
|---|---|
| Корректность | Независимые эталонные тесты проходят; размеры равны Go; SSIM с Go ≥ 0,98 |
| Безопасность | Fuzz декодера в CI, бюджеты из заголовка, изоляция и секреты как выше |
| Ресурсы | Пиковый RSS и время в бюджетах на самых тяжёлых допустимых входах под лимитом cgroup |
| Эксплуатация | Закреплённый компилятор с проверкой контрольной суммы, воспроизводимая сборка, CI проекта без отключённых проверок, второй человек, способный сопровождать |

**Эталонные тесты** не зависят от Go-реализации, потому что одинаковая ошибка
в обеих дала бы SSIM 1,0: ориентации 1–8 на несимметричной метке с известными
цветами углов, точные значения усреднения по площади при дробном коэффициенте,
прозрачность на белом по формуле, цвета однотонных полей, отсутствие
метаданных в JPEG Media.

**SSIM** — средний SSIM по яркости Y (BT.601) с окном Гаусса 11×11, σ = 1,5,
K1 = 0,01, K2 = 0,03, L = 255 (Wang и др., 2004); реализация — тестовый код
репозитория. Он ловит малые расхождения, но не заменяет эталонные тесты.

### Замер базовой линии Go, 2026-11-03

Реализация — `internal/media/preview`, сценарий — `baseline_test.go` того же
пакета:

```sh
PREVIEW_BASELINE=1 go test -run TestBaselineReport -v -timeout 60m ./internal/media/preview/
```

Стенд: VM на VMware, Ubuntu 24.04, 6 vCPU, 16 ГиБ, Go 1.27.3, libvips 8.15.1;
100 прогонов на изображение, пиковый RSS — отдельный процесс на задачу.

Две параллельные задачи на фото 12 Мп — 9,7 превью в секунду. Пустой дочерний
процесс занимает 5 МиБ.

Выводы:

- **Бюджеты выполняются с запасом:** p99 не выше 0,5 с при лимите 5 с; пиковый
  RSS 47 МиБ для JPEG и 98 МиБ для PNG на 24 Мп при лимите 256 МиБ. Лимит в
  24 миллиона пикселей подтверждён.
- **Память определяется буфером декодированных пикселей:** 1,5 байта на пиксель
  у JPEG (YCbCr 4:2:0) и 4 байта у PNG. Это свойство полного декодирования, а
  не языка: воркер на Zig с полным декодированием упрётся в тот же пол.
  Двукратная экономия памяти потребует потокового декодирования по строкам —
  это смена алгоритма, и по пункту 2 критерия её нужно сравнивать с таким же
  алгоритмом на Go.
- **Порог для Zig по времени** на 24 Мп: p95 не выше 230 мс для JPEG и 136 мс
  для PNG.
- У PNG на 12–24 Мп p99 заметно выше p95 (424 против 246 мс): вероятно, сборка
  мусора. Это стоит проверить в Z2 повторным замером с профилем.
- Время vips включает запуск процесса — около 0,8 с даже на 1 Мп — и с Go по
  времени не сравнимо. По памяти vips с уменьшением при декодировании близок к
  Go для JPEG и экономнее для PNG на 24 Мп (62–80 против 98 МиБ).

## Последствия

Два контейнера, сеть и сертификат mTLS, строка в списке RPC (Media → воркер),
таблицы задач, объектов и указателей с миграцией, сверщик и сборщик, маршрут
превью в Gateway и OpenAPI, заглушка в веб-клиенте. Каждый шаг — отдельный PR
после Z2.

## Приёмочные тесты (этап Z3)

1. Повреждённые, обрезанные и «бомбы» декомпрессии — `failed`, без падения Media.
2. Изображение больше 24 Мп или тяжелее бюджета памяти — `skipped`, оригинал
   скачивается.
3. Неверный ответ декодера (другие размеры, неверная длина, больше 320) отклоняется.
4. Превью недоступно не участнику и пользователю, удалённому из комнаты.
5. Два планировщика не берут одну задачу; ответ после истечения аренды не
   публикуется.
6. Во время `pending` и `failed` задачи v2 и при падении между S3 и БД байты и
   указатель v1 не меняются.
7. Падение между публикацией файла и постановкой задачи: сверщик создаёт задачу.
8. Таймаут, падение и OOM декодера: повторы ограничены, второй контейнер и
   загрузки работают.
9. Недоступность S3 и БД Media: задачи ждут в `pending` без расхода попыток и
   завершаются после восстановления.
10. Оригиналы с EXIF, GPS, ICC, комментариями, progressive и 4:4:4: превью —
    baseline 4:2:0 без APPn и COM; ориентация 1–8 применяется.
11. gRPC: запросы больше 4 МиБ и ровно 10 МиБ проходят, больше лимита отклоняются.
12. Fuzz разбора ответа декодера и запроса превью.
