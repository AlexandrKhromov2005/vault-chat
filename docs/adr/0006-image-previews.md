# ADR 0006: превью изображений — контракт, изоляция и критерий для Zig

Статус: предложено. Дата: 2026-11-03. Этап Z1 из
[ARCHITECTURE §12.2](../../ARCHITECTURE.md#122-zig-isolated-media-processing);
владелец направления — Tagir. Замер базовой линии на Go — следующий PR этого
этапа; сравнение с Zig — этап Z2.

## Контекст

Media принимает PNG и JPEG до 10 МиБ и не больше 40 миллионов пикселей по
заголовку, хранит оригинал в приватном S3 и отдаёт его только участникам
комнаты ([files](../media/files.md)). Превью нет: веб-клиент показывает вложение
кнопкой скачивания.

Ограничения, которые определяют дизайн:

- **Память.** Декодированное изображение занимает до 4 байт на пиксель:
  40 миллионов пикселей — около 160 МиБ только на пиксели, а у контейнера Media
  на VPS `mem_limit` 256 МиБ. Декодирование в процессе Media ставит под угрозу
  загрузку и скачивание всех файлов. Поэтому превью делается в отдельном процессе
  **независимо от языка** — изоляция и выбор между Go и Zig решаются раздельно.
- **Недоверенный ввод.** Файл прошёл проверку сигнатуры и заголовка, но не
  санитизацию; декодер разбирает данные злоумышленника.
- **Нет измеренного узкого места**, которое требовало бы Zig: выигрыш нужно
  показать замером, а критерий записать до сравнения.

## Контракт превью

| Параметр | Значение |
|---|---|
| Вход | Файл с типом `image/png` или `image/jpeg`, определённым Media по содержимому |
| Размер | Длинная сторона не больше 320 px, пропорции сохраняются, меньшие изображения не увеличиваются |
| Ориентация | EXIF Orientation 1–8 у JPEG применяется к превью |
| Выход | JPEG baseline, качество 80, 4:2:0; прозрачность PNG накладывается на белый |
| Метаданные | Не переносятся: EXIF, GPS, ICC и комментарии в превью отсутствуют |
| Цвет | sRGB; встроенный ICC-профиль игнорируется в первом этапе |
| Детерминизм | Одинаковый вход и версия воркера дают одинаковые байты |

Отличия, которые меняют результат, — кодек, метод уменьшения, учёт ICC —
фиксируются при сравнении отдельно: выигрыш другой библиотеки не засчитывается
языку.

## Решение

### Поток

1. После публикации файла Media ставит задачу `(file_id, preset "p320",
   worker_version)`; состояние превью — в новой таблице БД Media:
   `pending`, `ready`, `failed`, `skipped` (слишком большое или не изображение).
2. Планировщик Media отправляет воркеру байты оригинала (до 10 МиБ) и
   параметры пресета; воркер возвращает превью (до 256 КиБ) или код ошибки.
3. Media проверяет ответ: это JPEG, размеры в пределах пресета, байты в пределах
   бюджета, заголовок разбирается тем же валидатором. Только затем пишет объект
   `preview/<file_id>/p320` в тот же приватный бакет и переводит строку в `ready`
   условным обновлением.
4. `GET /api/v1/files/{file_id}/preview` отдаёт превью с той же проверкой
   членства через Chat, что и оригинал, и теми же заголовками
   (`private, no-store`, `nosniff`). Пока превью нет, ответ `404`, и клиент
   показывает заглушку.

### Идентичность задачи и дубли

Ключ задачи — `(file_id, preset, worker_version)`; ключ объекта определяется им
же. Повтор после падения перезаписывает тот же объект теми же байтами, а
переход в `ready` выполняет только первое успешное условное обновление.
Конфликтующих результатов не бывает: новая версия воркера — новая задача, старое
превью отдаётся до готовности нового.

### Изоляция воркера

- Отдельный контейнер `media-preview` в собственной `internal`-сети только с
  Media. Нет доступа к S3, БД, Auth, Chat, Redis и наружу; секретов нет.
- Файловая система только для чтения, без capabilities, `no-new-privileges`,
  непривилегированный пользователь, лимиты памяти, CPU и числа процессов.
- Воркер получает байты, а не пути или URL; клиентские данные не выбирают файлы.
- Связь Media → воркер — gRPC по mTLS с идентичностью сервиса, как остальные RPC
  ([ADR 0001](0001-internal-mtls.md)); воркер ничего не вызывает сам.

## Бюджеты

| Параметр | Значение |
|---|---|
| Вход | ≤ 10 МиБ (лимит загрузки) |
| Пиксели для превью | ≤ 24 миллиона; больше — `skipped`, оригинал не трогается |
| Память контейнера воркера | 256 МиБ на задачу; каждая задача — отдельный экземпляр воркера |
| Параллельные задачи | 2 на установку |
| Очередь | Планировщик берёт из БД не больше 256 задач за проход; остальные ждут в БД |
| Время | ≤ 2 с CPU и ≤ 5 с на задачу; превышение — отмена |
| Выход | ≤ 256 КиБ, ≤ 320 × 320 |
| Повторы | 2, с задержкой 30 с и 5 мин; затем `failed` |

24 миллиона пикселей в RGBA — около 96 МиБ: остаётся запас на копию при
уменьшении и рабочие буферы кодека в пределах 256 МиБ. Точные значения
пересматриваются по замеру базовой линии.

## Поведение при сбоях

| Сбой | Поведение |
|---|---|
| Таймаут, падение или OOM воркера | Попытка не удалась, перезапуск контейнера; оригинал и Media не затронуты |
| Повреждённый или обрезанный файл | `failed` без повторов, заглушка |
| Неверный ответ воркера | Отбрасывается проверкой Media, считается неудачей |
| S3 или БД Media недоступны | Задача остаётся `pending` и повторяется планировщиком |
| Пользователь удалён из комнаты | Превью недоступно ему так же, как оригинал |
| Очередь заполнена | Новые задачи ждут в БД; загрузка не замедляется |

## Базовая линия и критерий для Zig

Сначала на одном оборудовании и синтетическом наборе изображений измеряется
реализация этого контракта на Go: стандартные `image/jpeg` и `image/png` и
уменьшение усреднением по площади, реализованное в самом воркере. Один и тот же
алгоритм уменьшения переносится в Zig, поэтому сравнение измеряет язык, а не
библиотеку. Метрики: p50/p95/p99 времени задачи, пропускная способность
при двух параллельных задачах, пиковый RSS процесса, размер результата. Для
справки — существующий инструмент с уменьшением при декодировании (`libvips`).
Набор генерируется детерминированно в тестах: «фото» (градиенты и шум, JPEG
качества 90), «скриншот» (плоские цвета и резкие границы, PNG) и PNG с
прозрачностью; 1, 4, 12 и 24 мегапикселя.

**Критерий принятия Zig, записанный до сравнения.** Воркер на Zig внедряется,
только если на том же наборе и оборудовании, при том же контракте:

1. p95 времени для 12 и 24 мегапикселей ниже базовой линии Go хотя бы в 2 раза
   **или** пиковый RSS ниже хотя бы в 2 раза;
2. выигрыш сохраняется при сравнении с Go, использующим тот же алгоритм
   уменьшения, то есть объясняется не только другой библиотекой кодека;
3. результат визуально эквивалентен: те же размеры, SSIM с результатом Go не
   ниже 0,98;
4. закреплённый компилятор, воспроизводимая сборка, fuzz и CI для воркера
   реализуемы без отключения проверок проекта.

Иначе остаётся Go. Учебный эксперимент не считается доказательством
производительности в продакшне.

## Последствия

Новый контейнер, сеть и сертификат mTLS, строка в списке RPC (Media → воркер),
таблица состояний превью и миграция, маршрут превью в Gateway и OpenAPI,
заглушка в веб-клиенте. Каждый шаг — отдельный PR после Z2.

## Приёмочные тесты (этап Z3)

1. Повреждённые, обрезанные и «бомбы» декомпрессии — `failed`, без падения Media.
2. Изображение больше 24 миллионов пикселей — `skipped`, оригинал скачивается.
3. Неверный ответ воркера (не JPEG, слишком большой, другие размеры) отклоняется.
4. Превью недоступно не участнику и пользователю, удалённому из комнаты.
5. Дубль задачи и повтор после падения публикуют одно и то же превью один раз.
6. Таймаут, падение и OOM воркера: повторы ограничены, загрузки продолжаются.
7. Недоступность S3 и БД Media: задачи остаются `pending` и завершаются после восстановления.
8. EXIF и GPS отсутствуют в превью; ориентация 1–8 применяется.
9. Fuzz разбора ответа воркера и запроса превью.
