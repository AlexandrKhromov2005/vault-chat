# ADR 0004: кэш публичных профилей в Redis

Статус: предложено. Дата: 2026-11-03.

## Контекст

План защиты требует кэш данных приложения с источником истины, ключами, TTL,
инвалидацией и поведением при отказе ([требования](../requirements.md)); сейчас
Redis хранит только счётчики rate limiter. Кандидаты по коду `main`:

- **Проверка сессии (`ValidateToken`)** — самый частый вызов Auth: каждый
  защищённый запрос, каждый RPC Chat и Media, каждое событие WebSocket и раз в
  секунду на открытое соединение. Не кэшируется: проверка активности сессии в БД
  при каждом обращении — требование внешнего ревью (пункт 8), кэш продлил бы
  жизнь отозванной сессии.
- **Комнаты и членство** — строка комнаты меняется с каждым сообщением
  (`message_sequence`), а проверка членства намеренно идёт в той же транзакции,
  что и запись (пункт 10). Кэш нарушил бы эти инварианты.
- **Публичный профиль** `{user_id, username}` — имя неизменяемо, удаления
  аккаунтов в коде нет. Сейчас `GET /api/v1/users/{id}` стоит два RPC в Auth
  (`ValidateToken` и `GetUser`) и три запроса к БД; `GetUser` повторно проверяет
  сессию и читает всю строку пользователя.

Выигрыш скромный: веб-клиент уже держит профили в памяти на время сессии, так
что Gateway получает примерно один запрос на собеседника после загрузки
страницы. Кэш выбран потому, что это единственные данные, которые часто
читаются, почти не меняются и не участвуют в проверке прав.

## Решение

Gateway кэширует ответ `GetUser` в Redis, после аутентификации вызывающего.

- **Источник истины** — таблица `users` в БД Auth. Кэш хранит только публичную
  проекцию `{"user_id","username"}`: email, хэш пароля и состояние подтверждения
  в Redis не попадают.
- **Ключ** `cache:profile:v1:<user_id>`; `user_id` уже проверен как
  канонический UUID. Версия в ключе позволяет сменить формат без очистки.
- **Чтение.** Middleware аутентификации отрабатывает как сейчас: без
  действующей сессии ответ из кэша не выдаётся. Попадание — ответ без RPC
  `GetUser`. Промах — `GetUser`, затем запись в кэш.
- **TTL** 10 минут для найденного профиля. Отсутствующий аккаунт (`404`)
  кэшируется на 1 минуту: UUID новых аккаунтов случайны и не совпадут, а
  повторный перебор одного id не нагружает Auth.
- **Инвалидация.** Имя не меняется, поэтому активная инвалидация не нужна.
  Удаление аккаунта существует только как ручная операция в БД: процедура
  оператора дополняется удалением ключа, иначе профиль виден не дольше TTL.
  Если появится смена имени или удаление в коде, Auth будет удалять ключ в той
  же операции, а TTL останется верхней границей.
- **Поиск** (`SearchUsers`) не кэшируется: результаты по префиксу меняются с
  каждой регистрацией, а кэш расширил бы перечисление каталога.

## Границы доверия и бюджеты

- Кэш доступен только Gateway, в сети событий, под тем же паролем Redis.
  Запись в Redis по-прежнему позволяет подменить ответ, но не выдать данные,
  которых нет в публичной проекции. Каталог и без кэша доступен любому
  аутентифицированному участнику установки.
- Значение не больше 128 байт; число ключей ограничено числом разных профилей,
  запрошенных за 10 минут, а частота — существующим лимитом на пользователя
  (120 в минуту). Тысяча профилей — около 0,2 МиБ.
- На VPS Redis ограничен 64 МиБ с политикой `allkeys-lru`: при нехватке памяти
  он вытеснит и счётчики rate limiter, что обнуляет лимит. Поэтому записи кэша
  не должны занимать больше 8 МиБ: метрика размера кэша и алерт на рост
  `evicted_keys`. Если бюджет станет тесным, кэш переезжает в отдельную базу
  Redis с собственным лимитом, а не повышает общий.

## Поведение при сбоях

| Сбой | Поведение |
|---|---|
| Redis недоступен или отвечает дольше 250 мс | Промах: профиль берётся из Auth, ответ не меняется |
| Значение в кэше повреждено | Промах, ключ перезаписывается ответом Auth |
| Auth недоступен | Попадания обслуживаются; промахи дают ту же ошибку, что сейчас |
| Сессия отозвана | Middleware отклоняет запрос до обращения к кэшу |

## Альтернативы

- **Без серверного кэша.** Клиентского кэша хватает для нагрузки, но требование
  о кэше данных останется незакрытым.
- **Кэш в памяти Gateway.** Без сети, но у каждой реплики свой, и на защите нечем
  показать общий TTL и попадания между экземплярами.
- **Кэш внутри Auth.** Сохранял бы проверку сессии в `GetUser`, но не убирал RPC.

## Последствия

Gateway получает клиент кэша поверх существующего клиента Redis с таймаутом
250 мс. Метрики: `vault_profile_cache_requests_total{result="hit|miss|error"}` и
число ключей кэша; панель в дашборде Gateway. В инструкцию по удалению аккаунта
добавляется удаление ключа.

## Приёмочные тесты

1. Первый запрос профиля — промах и один `GetUser`, второй — попадание без RPC.
2. После истечения TTL (сдвиг времени в тестовом Redis) — снова промах.
3. Без токена и с отозванной сессией — `401` даже при заполненном кэше.
4. В Redis записаны только `user_id` и `username`.
5. `404` кэшируется на минуту; после неё запрос снова идёт в Auth.
6. Redis недоступен — профиль отдаётся из Auth, ошибка учтена в метрике.
7. Повреждённое значение — промах и перезапись.
8. Метрики попаданий и промахов отражают сценарии 1, 2 и 6.
