# ADR 0010: отдельная БД у каждого сервиса

Статус: принято. Дата: 2026-11-24. Отдельные экземпляры PostgreSQL действуют
с октября 2026, раздельные роли — после внешнего ревью 24 октября
([требования](../requirements.md), п. 9 и 13); этот ADR записывает решение
задним числом.

## Контекст

Auth хранит хеши паролей и сессии, Chat — переписку, Media — метаданные
файлов, а сами файлы лежат в S3. Утечка или ошибка в одном сервисе не должна
давать чтение или запись данных другого. При этом данные связаны: сообщение
ссылается на пользователя и на файлы, файл — на комнату.

## Решение

- **Три экземпляра PostgreSQL 16**: `postgres` (`auth_db`), `chat-postgres`
  (`chat_db`), `media-postgres` (`media_db`), каждый со своим томом, паролями и
  internal-сетью `auth-data`, `chat-data`, `media-data`. В сеть БД входят только
  её сервис и его задача миграции. Порты БД не публикуются. Так устроен VPS
  Compose; локальный Compose для разработки публикует БД, Redis и MinIO на
  127.0.0.1, его сети не internal, а Redis без пароля.
- **Две роли на БД.** Задача `*-migrate` подключается владельцем схемы,
  применяет миграции своего сервиса (`migrations/<service>`) и выдаёт права
  роли `*_app`. Рабочий контейнер получает только `*_app`: DML без DDL,
  без суперпользователя, `CREATEDB`, `CREATEROLE` и `BYPASSRLS`. Пароль
  владельца в рабочий контейнер не передаётся.
- **Объекты S3** доступны только Media: отдельный пользователь с правами на
  один бакет. Root-ключи, кроме самого MinIO, есть только у одноразовой
  задачи `s3-init`.
- **Нет межсервисного SQL.** Код сервиса не линкует хранение, миграции и
  бизнес-логику другого сервиса; чужие данные читаются только через RPC
  владельца ([ADR 0009](0009-internal-grpc.md)). Между БД нет внешних
  ключей: Chat хранит UUID пользователей и файлов как значения.
- **Ссылки проверяет владелец, в момент записи:**

| Связь | Кто проверяет | Как |
|---|---|---|
| Отправитель и участники комнаты | Chat | identity из `Auth.ValidateToken`; существование добавляемого пользователя — `Auth.GetUser` |
| Вложение в сообщении | Chat → Media | `Media.GetFile` до блокировки комнаты: файл готов, загружен отправителем, в той же комнате. Проверка не устаревает, потому что готовый файл, его комната и владелец неизменяемы |
| Доступ к файлу | Media → Chat | `Chat.GetRoom` при публикации и каждом скачивании: членство текущее |
| Членство при отправке | Chat | повторно под блокировкой комнаты в транзакции записи |

## Альтернативы

- **Одна БД со схемами на сервис.** Меньше памяти и одна точка backup.
  Отклонено: общий суперпользователь и процесс, ошибка в правах одной схемы
  открывает другие, а изоляция зависела бы только от GRANT.
- **Общая БД с внешними ключами между доменами.** Даёт ссылочную
  целостность, но связывает схемы и выпуск сервисов и позволяет любому
  сервису читать хеши паролей.
- **Репликация чужих данных (CDC, события `user.updated`).** Убирает
  синхронные вызовы, но добавляет брокер, задержку согласования и копии
  персональных данных в каждой БД. Пока объём не требует, данные читаются у
  владельца.

## Последствия

- **Согласованность по ссылкам — только в момент проверки.** Удаления
  пользователей и файлов нет, поэтому висячих ссылок сейчас нет. Когда
  появятся удаление аккаунта, редактирование или удаление сообщений и
  файлов (#193), нужен явный протокол: tombstone, событие удаления или
  периодическая сверка. Граница п. 10 ревью пересматривается вместе с ними.
- **Частичные отказы.** Загрузка файла пишет строку `pending`, объект S3 и
  публикует строку после повторного подтверждения членства. Сбой между
  шагами оставляет невидимую строку или объект; их собирает периодическая
  уборка ([Media](../media/files.md)).
- **Backup трёх БД согласован** только потому, что `scripts/vps/backup.sh`
  ставит Auth, Chat, Media, Gateway и MinIO на паузу на время дампов. Без
  паузы дампы были бы сняты в разные моменты.
- **Ресурсы.** Три PostgreSQL занимают больше памяти и соединений, чем один;
  на VPS у каждого свой лимит памяти.
- **Redis общий и не принадлежит одному сервису.** На VPS Auth, Chat и
  Gateway ходят в него с одним паролем: это шина событий и квоты, а не
  хранилище данных. Любой из этих сервисов может публиковать в каналы других
  и менять квоты Gateway. Содержимое события не подписано:
  скомпрометированный Auth или Chat может отправить пользователю поддельное
  событие чата, и проверка сессии перед событием этого не заметит. История и
  права остаются в PostgreSQL, поэтому догрузка вернёт настоящие данные.
  При недоступности Redis общие лимиты Gateway пропускают запросы (fail
  open), а квоты входа и регистрации закрываются. Раздельных Redis ACL для
  сервисов пока нет.

## Проверки

- `TestServicesLinkOnlyTheirOwnCodeAndData` (`tests/architecture`): ни один
  пакет и бинарник сервиса не зависит от хранения или бизнес-логики другого
  сервиса и не встраивает `migrations`; миграции встраивает `cmd/migrate`.
- `scripts/check-deployment.sh`: рабочий сервис подключается ролью `*_app`,
  стартует после своей миграции, а сеть его БД не пересекается с сетями
  других сервисов; MinIO — только в сети `objects`, ключи Media не равны root.
- `TestRuntimeRoleHasDMLButCannotChangeSchema` (`tests/integration`): роль
  `auth_app`, выданная `ProvisionRuntime`, читает таблицы, но не создаёт, не
  меняет и не удаляет таблицы и схемы и не имеет привилегий
  суперпользователя. `chat_app` и `media_app` выдаются тем же кодом.
- `TestScopedS3CredentialsCannotAccessOtherBuckets`
  (`internal/media/storage`): ключ Media не пишет в чужой бакет, не создаёт
  бакеты и не видит чужие в списке.
- `TestChatAttachments_PersistenceAndRetry`, `TestUploadAndAuthorizedDownload`
  и `TestCompose_PrivateAttachments`: вложения проверяются у владельца, а
  посторонний не скачивает файл.
- `test_failed_dump_unpauses_services_and_never_marks_complete`
  (`tests/ops/test_vps.py`): неудачный дамп снимает паузу и не помечает backup
  завершённым.

```sh
go test -count=1 ./tests/architecture/
sh scripts/check-deployment.sh
```
