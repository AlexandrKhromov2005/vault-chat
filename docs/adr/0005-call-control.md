# ADR 0005: управление звонками — контракт, бюджеты и сравнение Go и Erlang/OTP

Статус: предложено. Дата: 2026-11-03. Этап E1 из
[ARCHITECTURE §12.1](../../ARCHITECTURE.md#121-erlangotp-call-control); владелец
направления — Tagir. Кода нет: прототипы обоих кандидатов — этап E2.

## Контекст

Звонков в проекте нет. План предлагает оценить Erlang/OTP для управления
звонками против Go, не считая заранее, что лёгкие процессы дают выигрыш: ни
одно измерение пока не указывает на Go как на ограничение. Чтобы сравнение было
честным, оба кандидата реализуют один и тот же контракт из этого документа.

Ограничения текущей системы, которые определяют дизайн:

- WebSocket принимает от клиента только кадры `auth` до 4096 байт; неизвестный
  тип закрывает соединение ([realtime](../chat/realtime.md)). SDP аудиозвонка —
  1–4 КБ.
- События до клиентов идут через Redis Pub/Sub и могут теряться; авторитетные
  данные клиент перечитывает по REST.
- Auth авторитетен для сессий, Chat — для членства; RPC между сервисами идут по
  mTLS с явным списком разрешённых методов ([ADR 0001](0001-internal-mtls.md)).
- Одна установка — один VPS.

## Первый сценарий

Аудиозвонок один на один в личном диалоге между двумя браузерами: вызов,
звонок на всех устройствах собеседника, принять, отклонить, отменить,
соединиться, завершить. Видео, группы, запись и Android (этап E4) — отдельные
решения.

## Решение

### Компоненты

- **Calls** — новый сервис управления звонками, кандидат на Go или Erlang/OTP.
  Хранит авторитетное состояние в собственной PostgreSQL, проверяет сессию
  через `Auth.ValidateToken` и личный диалог через `Chat.GetRoom`, публикует
  события в существующие каналы `chat:user:<id>`.
- **Gateway** принимает REST-команды и пересылает их в Calls по gRPC + mTLS;
  события звонков доходят до клиентов тем же WebSocket.
- **Медиа** — WebRTC напрямую между браузерами, шифрование DTLS-SRTP;
  **coturn** на VPS для клиентов за NAT. Звук не проходит через Calls, Chat или
  Redis.

P2P выбран для 1:1: сервер видит только сигнализацию, TURN нужен лишь части
соединений, трафик и сопровождение дешевле SFU. Групповые звонки потребуют SFU
(например, LiveKit) отдельным решением.

### Состояния и команды

```
ringing --accept--> connecting --connected--> active --end--> ended
ringing --reject | cancel | timeout--> ended
connecting --timeout | end--> ended
```

Каждый переход — условное обновление строки звонка в БД (`WHERE state = ... AND
version = ...`) с увеличением `version`. Поэтому два устройства, принявшие
звонок одновременно, и несколько экземпляров Calls не могут выполнить
противоречащие переходы: выигрывает первый commit, остальные получают `409` и
текущее состояние.

| Команда (REST через Gateway) | Кто | Идемпотентность |
|---|---|---|
| `POST /api/v1/calls {room_id, client_call_id}` | участник личного диалога | `client_call_id` |
| `POST /api/v1/calls/{id}/accept` | вызываемый, одно устройство | `command_id` |
| `POST /api/v1/calls/{id}/reject`, `.../cancel`, `.../end` | участник по роли | `command_id`; повтор завершённого — `200` |
| `POST /api/v1/calls/{id}/signal {kind, payload, seq}` | участник активного звонка | `seq` на отправителя; повтор и старый `seq` отбрасываются |
| `POST /api/v1/calls/{id}/heartbeat` | устройство участника | — |
| `GET /api/v1/calls/{id}`, `GET /api/v1/calls?active=true` | участник | чтение для сверки после переподключения |
| `POST /api/v1/calls/{id}/turn` | устройство участника | новые учётные данные TURN |

События WebSocket: `call.ringing`, `call.accepted` (с id принявшей сессии —
остальные устройства перестают звонить), `call.signal`, `call.ended` (с
причиной). Каждое несёт `version`; клиент, увидевший пропуск или
переподключившийся, читает `GET /api/v1/calls/{id}`.

Кандидаты ICE и SDP вызываемого пересылаются только после `accept`: звонящий не
узнаёт IP-адреса собеседника, если тот не ответил.

## Модель угроз

| Угроза | Мера |
|---|---|
| Звонок незнакомому или спам вызовами | Только участник личного диалога; лимиты вызовов; занятый пользователь — `409 busy` |
| Чужие команды для звонка | Каждая команда проверяет сессию и роль в звонке; id звонка не дают прав |
| Огромный или вредный SDP/ICE | Только текст UTF-8 в пределах бюджета; сервер не разбирает SDP, браузер собеседника разбирает своим стеком |
| Отозванная сессия или выход из диалога во время звонка | Calls проверяет сессию на каждой команде и раз в 5 секунд для активных звонков; при отказе — `call.ended` и новые учётные данные TURN не выдаются |
| TURN как открытый прокси или вход во внутренние сети | Учётные данные только участникам, имя `call_id:user_id`, срок 10 минут (HMAC, `use-auth-secret`); `denied-peer-ip` для частных, loopback и link-local сетей, `no-multicast-peers` |
| Подмена отпечатков DTLS сервером сигнализации | Сервер доверенный; защита от него требует проверки отпечатков собеседниками — вне первого этапа |
| Утечка метаданных | Логи и метрики без SDP, кандидатов и IP; в БД хранятся участники, состояние и время |

**Предел серверного завершения.** Сервер завершает сигнализацию и перестаёт
выдавать учётные данные TURN, но не может разорвать уже установленный P2P-поток
между браузерами; поток через TURN живёт до истечения выделения (до 10 минут).
Честные клиенты закрывают соединение по `call.ended`.

## Бюджеты

| Параметр | Значение |
|---|---|
| Звонков `ringing` + `connecting` + `active` на пользователя | 1 |
| Активных звонков на экземпляр / на установку | 200 / 200 |
| Новых вызовов на пользователя | 10 в минуту, burst 3 |
| Команд `signal` на устройство в звонке | 20 в секунду, не больше 200 за звонок |
| SDP | ≤ 8 КиБ; кандидат ICE ≤ 512 байт, ≤ 32 на устройство |
| Тело любой команды | ≤ 16 КиБ |
| Звонок `ringing` | 30 с |
| `connecting` → `active` | 30 с |
| Heartbeat | каждые 15 с; без него 45 с — звонок завершается |
| Длительность звонка | ≤ 2 часа |
| Ответы Auth, Chat и БД | ≤ 2 с на вызов |
| Порты TURN relay | 100 UDP-портов: до 50 звонков через relay, около 13 Мбит/с для Opus |
| Остановка | новые вызовы отклоняются сразу, текущие состояния уже в БД, ожидание ≤ 15 с |

Перегрузка: новые вызовы — `503` с `Retry-After`, текущие звонки продолжаются.
Очереди и повторы ограничены при недоступности Redis, Auth, Chat и БД.

## Поведение при сбоях

| Сбой | Поведение |
|---|---|
| Auth или Chat недоступны | Новые вызовы и `accept` отклоняются (fail closed); `end` выполняется без них |
| БД Calls недоступна | Команды получают `503`; переходы не выполняются в памяти |
| Redis недоступен | События теряются; клиенты сверяются по REST, звонки по таймаутам завершаются |
| Падение или перезапуск Calls | Состояние в БД; таймеры восстанавливаются из сроков в строке; при старте просроченные звонки завершаются |
| Потеря `call.accepted` или `call.ended` | Клиент сверяется по `version` и heartbeat-ответу, который несёт текущее состояние |
| coturn недоступен | Работают только прямые соединения; ошибка учтена в метрике |

Перезапуск супервизора OTP сам по себе состояние не восстанавливает: у обоих
кандидатов источник истины — строка в БД, процесс держит лишь таймеры и порядок
команд.

## Сравнение кандидатов

Оба реализуют контракт выше, ходят в Auth и Chat по gRPC + mTLS, пишут
состояние в PostgreSQL и отдают метрики Prometheus.

| Критерий | Go | Erlang/OTP |
|---|---|---|
| Модель звонка | горутина и мьютекс или очередь на звонок | процесс `gen_statem` на звонок: таймеры и порядок команд встроены |
| gRPC + mTLS с URI SAN | общий код `rpctls` | `grpcbox` и `ssl`; проверку SPIFFE URI и список RPC нужно реализовать и протестировать заново |
| PostgreSQL | `pgx`, как в остальных сервисах | `epgsql` |
| Метрики и логи | `internal/shared/telemetry` | `prometheus.erl`; формат JSON-логов согласовать |
| Сборка и CI | существующие `xmake ci`, golangci-lint, govulncheck | закреплённый OTP и rebar3, dialyzer, EUnit/Common Test, отдельные задачи xmake и проверка уязвимостей зависимостей |
| Образ и развёртывание | тот же Dockerfile | отдельный образ релиза OTP |
| Опыт команды | есть у всех | владелец осваивает; ревью сложнее |

Гипотезы для E2 на одном одноразовом стенде и одинаковой нагрузке:
p95/p99 установки звонка, пропускная способность команд, ошибки, CPU и пиковая
память на 200 активных звонков, время восстановления после `kill -9`,
корректность при дублях и переупорядочивании команд. Стоимость TURN
измеряется отдельно. По решению E5 Go остаётся, если OTP не даёт согласованного
выигрыша, оправдывающего второй runtime.

## Последствия

Новый сервис, своя БД, роли и сеть, сертификат mTLS и строки в списке RPC
(Gateway → Calls; Calls → `Auth.ValidateToken`, `Chat.GetRoom`), coturn с
открытыми UDP-портами на VPS, секрет TURN и его ротация, новые события в
протоколе WebSocket и REST в OpenAPI. Каждый из этих шагов — отдельный PR после
E2.

## Приёмочные тесты (этап E3)

1. Звонок вне личного диалога и чужие команды отклоняются.
2. Два устройства принимают одновременно — `active` ровно одно, второе получает `409`.
3. Дубли и переупорядоченные `signal` и команды не меняют результат.
4. Потерянные `call.accepted` и `call.ended` восстанавливаются сверкой.
5. Отзыв сессии и выход из диалога во время звонка завершают его за ≤ 5 с.
6. SDP, кандидаты и тела команд сверх бюджета отклоняются; fuzz разбора команд.
7. Перезапуск Calls во время `ringing` и `active` — состояния и таймеры сохраняются.
8. Недоступность Auth, Chat, БД и Redis ведёт себя по таблице сбоев.
9. Перегрузка: новые вызовы получают `503`, текущие звонки не затронуты.
10. TURN не соединяется с частными и loopback-адресами; просроченные учётные данные отклоняются.
