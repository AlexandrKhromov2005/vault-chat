# ADR 0003: сохраняемая доставка push-сигналов через NATS JetStream

Статус: предложено. Дата: 2026-11-03. Реализация — после слияния push-диспетчера
(#112) и согласования с его автором.

## Контекст

План защиты требует один полезный поток через брокер с сохраняемым consumer и
подтверждением обработки ([требования](../requirements.md)); трактовка
требования курса ещё не согласована. Асинхронные потоки сейчас:

| Поток | Транспорт | Когда теряется | Как восстанавливается |
|---|---|---|---|
| События чата → WebSocket | Redis Pub/Sub `chat:user:<id>` | отказ Redis или Gateway, переполнение очереди Chat (1024 изменения) | догрузка по `sequence` и пересинхронизация комнат ([realtime](../chat/realtime.md)) |
| Отзыв сессии Auth → Gateway | Redis Pub/Sub | отказ Redis | БД Auth авторитетна, Gateway проверяет сессию раз в секунду |
| Почта Auth → SMTP | транзакционный outbox в PostgreSQL Auth | не теряется | повтор из outbox с арендой и счётчиком попыток |
| Push Chat → Auth → FCM (#112) | Redis Pub/Sub `push:signal:v1` | перезапуск или недоступность Auth, отказ Redis | нет: только следующий сигнал или синхронизация, начатая самим клиентом |

Push — единственный поток, потерю которого сервер не восстанавливает. Auth
перезапускается при каждом обновлении и при ротации mTLS-сертификатов; сигналы,
опубликованные в это время, пропадают, и телефон не узнаёт о сообщении.

## Решение

Перевести push-сигналы Chat → Auth с Redis Pub/Sub на NATS JetStream. Живые
события остаются на Pub/Sub — их уже восстанавливает догрузка; почта остаётся
на outbox. Содержимое сигнала не меняется: комната и получатели без текста, имён,
отправителя и id сообщения.

**Гарантия.** Доставка «хотя бы один раз» начинается после `PubAck` и
заканчивается принятием сообщения FCM. Между commit сообщения в БД Chat и
`PubAck`, а также после принятия FCM (устройство вне сети дольше TTL, вытеснение
на стороне FCM) доставка остаётся best effort. Повторный push возможен и
безопасен, потому что синхронизация комнаты на клиенте идемпотентна; collapse
key FCM дубликаты не устраняет: он сворачивает только ещё не доставленные
сообщения и хранит не больше четырёх ключей на устройство.

- **Stream** `PUSH_SIGNALS`, subject `push.signal.v1`, хранение на диске,
  retention `WorkQueue` (сообщение удаляется после ACK), `MaxAge` 1 час. Лимиты
  100 000 сообщений и 256 МиБ, `Discard: New`: при переполнении публикация
  отклоняется, а не вытесняет непрочитанное.
- **Публикация.** Фоновый воркер Chat, который уже публикует события после
  commit, публикует сигнал с ожиданием `PubAck` в пределах
  `CHAT_EVENT_PUBLISH_TIMEOUT` (1 с). `Nats-Msg-Id` — непрозрачный хэш id
  сообщения и номера части (большие комнаты делятся на части по 500
  получателей); окно дедупликации 2 минуты гасит повторную публикацию при ретрае.
- **Consumer** Auth: один durable pull consumer `auth-push`, `AckExplicit`,
  `AckWait` 30 с, без `BackOff`. Пока сигнал ждёт в окне схлопывания или его
  отправка идёт, Auth каждые 10 с отправляет `InProgress`, который продлевает
  `AckWait`; доставка без прогресса дольше 30 с означает падение обработчика.
- **Повторы.** Временная ошибка (БД Auth, сеть, `5xx`/`429` FCM) —
  `NakWithDelay` по номеру доставки из метаданных: 5 с, 30 с, 2 мин, 10 мин.
  `MaxDeliver` 5; после пятой неудачи — `TERM`, счётчик и лог. Некорректный
  сигнал — `TERM` сразу, как сейчас.
- **Бюджет.** `MaxAckPending` — 20 сообщений. В сообщении до 500 получателей,
  значит одновременно в работе не больше 10 000 пар «пользователь — комната»,
  ровно бюджет диспетчера. Auth запрашивает новые сообщения только при
  свободных парах в этом бюджете.
- **Отметки на получателя.** После того как push пары «пользователь —
  комната» отправлен или получил окончательный ответ FCM, Auth записывает в
  свою БД отметку `(Nats-Msg-Id, user_id)` для каждого сигнала, слитого в этот
  push, с истечением через 2 часа. Сообщение подтверждается, когда отметка есть у
  всех его получателей; иначе — `NakWithDelay`, и повторная доставка отправляет
  только тем, у кого отметки нет. Падение после записи отметки повтора этому
  получателю не даёт; падение между принятием FCM и записью отметки даёт ему
  один повторный push.
- **TTL.** TTL push в FCM — остаток часа от времени сообщения в stream: сигнал
  будит устройство не позже чем через час после публикации, сколько бы он ни
  ждал в stream. Сигнал с истёкшим часом подтверждается без отправки.
- **Без outbox в Chat.** Сигнал — подсказка, а не данные: падение Chat между
  commit и публикацией теряет одно пробуждение, а сообщение клиент получит при
  синхронизации. Поток, который обязан соответствовать записи в БД, должен
  использовать транзакционный outbox, как почта.

## Границы доверия

- NATS — только во внутренней сети событий, без порта на хосте VPS. Соединения —
  TLS с private CA развёртывания ([ADR 0001](0001-internal-mtls.md)).
- Отдельные учётные данные: Chat может только публиковать в `push.signal.v1`,
  Auth — только читать consumer `auth-push`; остальное запрещено. Auth по-прежнему
  проверяет каждый сигнал: публиковать может любой, у кого есть права на subject.
- Хранилище JetStream — отдельный том с явным `-sd`: сейчас локальный контейнер
  запускается с `-js` без каталога и пишет в `/tmp`. В backup поток не входит:
  сигналы истекают за час, восстановление начинается с пустого stream.

## Поведение при сбоях

| Сбой | Поведение |
|---|---|
| Auth остановлен или перезапускается | Сигналы копятся в stream (до часа и лимитов) и доставляются после запуска |
| NATS недоступен | Отправка сообщений не затронута; Chat считает и отбрасывает сигналы, как сейчас при отказе Redis |
| Stream переполнен | Публикация отклоняется, Chat считает потерю и не блокируется |
| БД Auth или FCM временно недоступны | `NakWithDelay`, до 5 доставок, затем `TERM`, счётчик и лог |
| Обработчик Auth упал во время отправки | Через 30 с без `InProgress` сообщение доставляется снова; получатели с отметками пропускаются |
| FCM отвечает `UNREGISTERED` | Удаляется отправленный токен, сигнал подтверждается |

## Альтернативы

- **Оставить Pub/Sub.** Проще, но пробуждения во время перезапуска Auth теряются.
- **Redis Streams с группой потребителей.** Тоже сохраняет и подтверждает, без
  нового компонента. Не выбрано: Redis в проекте работает как fail-open кэш
  лимитов без гарантий хранения, а JetStream даёт `MaxAge`, дедупликацию,
  задержки повторов и права на subject без собственной реализации.
- **Outbox в БД Chat, который читает Auth.** Строгая согласованность, но Auth
  получает доступ к данным Chat или новый RPC ради подсказки.

## Последствия

Новый контейнер в продакшне: том хранения, сертификат и учётные данные Chat и
Auth (выпуск и ротация вместе с PKI из ADR 0001), мониторинг JetStream (длина
stream, ожидающие ACK, исчерпанные доставки) и алерт на рост очереди. Новая
зависимость `github.com/nats-io/nats.go`. Таблица отметок `(Nats-Msg-Id,
user_id)` в БД Auth с очисткой по сроку: до 500 строк на сообщение, не дольше
2 часов.

## Приёмочные тесты

1. Consumer Auth остановлен, отправлено сообщение, consumer запущен — получатель
   получает один push, отправитель — ни одного.
2. Падение после записи отметки получателя и до ACK — повторная доставка ему
   push не отправляет.
3. Падение между принятием FCM и записью отметки — этот получатель получает
   ровно один повторный push, получатели с отметками — ни одного.
4. Частичный успех: получателю A push ушёл, у B временная ошибка — `NakWithDelay`,
   повторная доставка отправляет только B.
5. Обработка дольше `AckWait` (окно схлопывания, медленный FCM) при работающем
   обработчике — `InProgress` не даёт повторной доставки.
6. В работе 20 неподтверждённых сообщений — 21-е не доставляется до ACK.
7. Сигнал, пролежавший в stream 50 минут, отправляется с TTL около 10 минут;
   сигнал старше часа подтверждается без отправки.
8. Одинаковый `Nats-Msg-Id` дважды в окне дедупликации — в stream одно сообщение.
9. Некорректный сигнал — `TERM`, без повторной доставки, учтён в метрике.
10. Временная ошибка FCM — повторы с задержками 5 с, 30 с, 2 мин, 10 мин и
    отправка после восстановления; после пятой неудачи — `TERM`; окончательная
    ошибка — ACK.
11. NATS недоступен — сообщение сохраняется и доходит по WebSocket, сигнал учтён
    как потерянный; после восстановления новые сигналы доставляются.
12. Учётные данные Chat не читают consumer, учётные данные Auth не публикуют.
13. Переполнение stream — публикация отклонена и учтена, Chat не блокируется.
