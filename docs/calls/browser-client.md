# Звонки в веб-клиенте

Аудиозвонок один на один в личном диалоге — клиентская часть
[ADR 0005](../adr/0005-call-control.md). Код: `web/static/app/calls.mjs`
(состояние звонка, команды, порядок сигналов), `call-media.mjs` (микрофон и
`RTCPeerConnection`), `call-panel.mjs` (панель звонка); тесты —
`web/test/calls.test.mjs`, `call-media.test.mjs` и `call-panel.test.mjs`.

## Поведение

- **Доступность.** После каждого подключения WebSocket клиент сверяет звонки
  через `GET /api/v1/calls?active=true`. Пока Gateway отвечает на этот путь
  `404`, кнопки «Позвонить» нет; сбой `503` доступность не меняет.
- **Устройство звонка** — вкладка, которая создала звонок или приняла его: только
  она открывает микрофон, создаёт `RTCPeerConnection`, шлёт сигналы и heartbeat.
  Другие вкладки тех же пользователей показывают звонок без звука и без
  микрофона. Вкладка после перезагрузки остаётся той же сессией Auth, но
  соединение не восстанавливает — может только завершить звонок.
- **Микрофон** запрашивается до `POST /api/v1/calls` и до `accept`: при отказе
  разрешения, отсутствии устройства или вне HTTPS вызов не создаётся и не
  принимается, вызываемый может отклонить звонок. Микрофон освобождается сразу
  при завершении, отклонении, отмене, ошибке, выходе из аккаунта и уходе со
  страницы, независимо от ответа сервера.
- **Команды** идемпотентны: при сетевой ошибке запрос повторяется до двух раз с
  тем же `command_id` (сигнал — с тем же `sender_seq`, также после `429`).
  Повторный клик не отправляет вторую команду, пока первая не завершилась.
  Отмена, проигравшая гонку с `accept` (`409`), завершает звонок через `end`.
- **Сигналы.** Звонящий шлёт `offer` до того, как начнётся сбор кандидатов;
  вызываемый отвечает `answer` только на `offer`. Кандидаты — JSON
  `{candidate, sdpMid, sdpMLineIndex, usernameFragment}` до 512 байт, не больше
  32 на устройство; `end-of-candidates` с пустым payload только в `connecting`.
  Сигналы собеседника применяются строго по `signal_seq`, каждый один раз. Событие
  не по порядку и любой пропуск догружаются через `GET .../signals?after=`.
  Сигналы своего устройства распознаются по `signal_seq` из ответа на `POST
  .../signal`, а если ответ потерян — по виду и payload. Описание сверх 8 КиБ,
  `answer` без `offer` и описание, отвергнутое браузером, завершают звонок.
  Некорректный кандидат отбрасывается.
- **Состояние** читается с сервера: события `call.*` — только повод его
  перечитать. Состояние не откатывается назад, а завершённый звонок не
  оживает от запоздалого ответа или события. Пока звонок в `ringing`, клиент
  опрашивает его раз в 3 с, пока соединение не установлено — сигналы раз в 1 с.
  Устройство звонка шлёт heartbeat каждые 15 с, другие вкладки перечитывают
  звонок с тем же интервалом. Когда ICE соединилось, отправляется `connected`.
  При `failed` клиент отправляет `end` (ICE restart — задача #162).
- **TURN.** Перед созданием соединения клиент вызывает `POST .../turn`. Если
  запрос не удался, используются только прямые соединения; сторонних
  STUN-серверов клиент не использует.
- **Выход из аккаунта** сначала завершает звонок (ждёт сервер не больше 2 с), уход
  со страницы — так, как успеет браузер; иначе звонок завершается по таймауту
  heartbeat (45 с). Ответы, пришедшие после выхода, отбрасываются.
- SDP, кандидаты и адреса не пишутся в консоль и не показываются.

## Ожидаемый контракт сервера

Production API (#156) и события (#157) ещё не выпущены. Клиент рассчитывает на
пути и тела из ADR 0005 и на поля ниже. При расхождении менять нужно
`parseCall`, `parseSignal` и `parseIceServers` в `calls.mjs`.

| Запрос | Ответ, который читает клиент |
|---|---|
| `POST /api/v1/calls {room_id, command_id}` | `201 {call_id, state}` |
| `POST .../{accept,reject,cancel,end,connected,heartbeat} {command_id}` | `{state}` |
| `POST .../signal {kind, payload, sender_seq}` | `{signal_seq}` |
| `GET /api/v1/calls/{id}`, `GET /api/v1/calls?active=true` | `{call_id, room_id, caller_id, callee_id, state}`, список — `{calls: [...]}` |
| `GET .../signals?after=N` | `{signals: [{signal_seq, kind, payload}]}`, по возрастанию |
| `POST .../turn {}` | `{ice_servers: [{urls, username, credential}]}` |

`caller_id` и `callee_id` нужны, чтобы показать входящий звонок, найденный при
сверке. Heartbeat клиент шлёт с `command_id`, как требует прототип. События
WebSocket: любой `type` с префиксом `call.` и полем `call_id`. Для
`call.signal` клиент может взять поля сигнала из события (`signal_seq`,
`kind`, `payload` на верхнем уровне или в `signal`); если их нет, он
догружает сигналы.

## Проверено и что осталось

Проверено юнит-тестами с подменёнными `getUserMedia`, `RTCPeerConnection` и
сервером: жизненный цикл звонящего и вызываемого, порядок и повторы сигналов,
отказ микрофона, гонки accept/reject/cancel, повторы команд, устаревшие ответы,
выход из аккаунта, бюджеты кандидатов и SDP.

Не проверено, пока нет production API: реальный разговор двух браузеров через
Gateway и live E2E сценарий приёмки #161. Звук через TURN при заблокированном
P2P проверяется после #158. Переподключение с ICE restart и смена сети — #162.
